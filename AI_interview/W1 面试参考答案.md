## W1-Q1 同步函数、线程和 async 协程有什么区别？

这个我一般会先从“**谁在等、怎么切换**”来理解。

同步函数最简单，就是当前这件事没做完，后面的代码就继续等。比如我调一个接口要 2 秒，这 2 秒当前执行流程基本就是卡在这里。

线程就不一样了。一个线程在等网络或者数据库的时候，操作系统可以去调度另一个线程，所以它比较适合阻塞型 I/O。不过线程不是没有成本，线程多了以后会有上下文切换、内存占用这些问题。

async 协程更轻一点。它一般跑在单线程事件循环里，代码执行到 `await`，而且这个 I/O 还没完成的时候，它会主动把执行权让出来，让其他协程先跑。

所以如果让我简单总结：

同步是一个一个做；线程是操作系统帮你切；协程是任务自己在合适的时候让。

像 FastAPI 这种很多请求都在等数据库、Redis、HTTP API 的场景，我会优先考虑 async。

但如果是 CPU 密集任务，比如模型计算或者大量 Python 运算，async 本身没有什么帮助，因为它不 await，就会一直占着事件循环。这时候更适合多进程、GPU 或者独立计算服务。

## W1-Q2 Python GIL 是什么？它是否意味着 Python 不能并发？

GIL 我一般不会把它理解成“Python 不能并发”，这个说法太绝对了。

GIL 是 CPython 里的全局解释器锁。传统情况下，同一个 Python 进程里，同一时刻通常只有一个线程在真正执行 Python 字节码。

所以它主要影响的是**CPU 密集型多线程并行**。

比如我写两个纯 Python 的大循环，开两个线程，通常并不会因为有两个 CPU 核就变成两倍速度。

但如果线程是在做网络请求、文件 I/O、数据库等待，这些操作很多时候会释放 GIL，这时候其他线程还是可以继续执行的。

另外 Python 还可以用 asyncio 做并发，或者多进程真正利用多核。

所以我自己的总结就是：

**GIL 限制的是同一进程里 Python 字节码的多线程并行，不代表 Python 不能做并发。**

## W1-Q3 为什么不建议把可变对象作为函数默认参数？

这个坑我觉得主要是因为 Python 的默认参数不是每次调用函数时重新创建的，而是在函数定义的时候就创建好了。

比如：

`def add_item(items=[]):`

这个 `[]` 实际上只创建一次。

第一次调用的时候，我往里面 append 一个值；第二次调用，它还是之前那个 list，所以之前的数据还在。

这就会出现一种很隐蔽的问题：我明明感觉每次调用都是新的，结果状态却被上一次调用保留下来了。

所以一般我会写成：

`items=None`

然后函数内部判断：

`if items is None:`
`    items = []`

这样每次调用才会创建新的 list。

所以核心不是“默认参数不能是 list”，而是：

**不要把会被修改的对象作为共享默认值。**

## W1-Q4 浅拷贝与深拷贝有什么区别？什么情况下容易踩坑？

这个我一般会先看对象里面有没有嵌套的可变对象。

浅拷贝只复制最外层。

比如有一个：

`[[1, 2], [3, 4]]`

我做浅拷贝以后，最外面的 list 确实是新的，但是里面两个小 list 还是原来的对象。

所以如果我修改里面的小 list，原对象也可能一起变化。

深拷贝则会继续往里面递归复制，通常里面的对象也会重新创建。

最容易踩坑的其实不是普通的一维 list，而是这种：

嵌套 dict、嵌套 list、配置对象、缓存结果。

因为表面看是两个对象，内部其实还是共用引用。

所以我的判断一般是：

如果只是简单数据结构，用浅拷贝就够了；

如果内部还有可变对象，而且两个副本必须完全独立，再考虑深拷贝。

不过 `deepcopy` 本身也有成本，而且有些复杂对象也不一定适合直接深拷贝，所以不是无脑用。

## W1-Q5 迭代器和生成器是什么关系？生成器有什么优势？

我一般把生成器理解成一种“更方便写迭代器”的方式。

迭代器本身就是一个可以不断取下一个值的对象，核心就是 `__iter__()` 和 `__next__()`。

生成器则是我在函数里写 `yield`，Python 就帮我把很多迭代器的状态管理做好了。

它最大的特点是**不会一次性把所有数据都算出来**。

比如我要处理一个很大的日志文件，如果我直接 `readlines()`，可能一次把几百万行都放进内存。

但如果我用生成器，就可以一行一行取，一边读一边处理。

所以它比较适合：

大文件、流式数据、批量数据处理、分页读取。

代价就是它通常是顺序消费的，遍历完以后不能像 list 一样随便再访问前面的元素。

所以我的理解就是：

**生成器用计算换内存，而且数据是按需产生的。**

## W1-Q6 Python 装饰器的本质是什么？为什么常使用 functools.wraps？

装饰器我一般不会死记语法，我会把它理解成：

**我不修改原函数内部代码，但是给这个函数外面包一层逻辑。**

比如原来有个函数：

`pay()`

我想在调用前做权限校验，调用后记录日志。

那装饰器实际上就是接收原函数，然后返回一个新的函数。

所以它本质上还是高阶函数加闭包。

比较常见的场景就是：

日志、权限、重试、缓存、统计耗时。

`functools.wraps` 的作用主要是保留原函数的信息。

因为如果不加 wraps，装饰以后系统看到的函数名可能变成 `wrapper`，文档字符串、注解这些也可能丢掉。

这对日志、调试、FastAPI 这种依赖函数签名的框架都会有影响。

所以我一般写装饰器时都会顺手加上 `@wraps(func)`。

## W1-Q7 上下文管理器解决什么问题？with 语句如何保证资源释放？

我觉得上下文管理器解决的是一个很实际的问题：

**资源打开以后，不管中间正常还是异常，都要保证能释放。**

比如文件。

如果我手动：

open → 操作 → close

中间突然抛异常，后面的 close 可能就执行不到了。

用了 `with` 以后，进入作用域时会调用 `__enter__`，离开的时候会调用 `__exit__`。

即使中间抛异常，退出逻辑通常还是会执行。

所以文件、锁、数据库事务这种资源特别适合用上下文管理器。

我自己的理解就是：

**把资源的申请和释放绑定到同一个代码块里，避免我自己忘记清理。**

## W1-Q8 Coroutine、Task 和 Future 分别是什么？

这个我一般按层级去理解。

首先调用一个 `async def` 函数，得到的是 Coroutine，也就是协程对象。

它这时候只是“一个以后可以执行的异步操作的逻辑”，不一定已经开始并发跑了。

如果我通过 `asyncio.create_task()` 把它包装成 Task，就相当于把它交给事件循环去调度。

Future 更底层一点，它表示的是：

**一个现在还没有，但是未来会有的结果。**

Task 本身其实也是 Future 的一种。

所以实际写业务时，我更多接触的是 Coroutine 和 Task。

Future 更多是底层库或者框架内部会直接使用。

我会简单记成：

Coroutine 是异步代码本身；

Task 是被调度中的协程；

Future 是未来结果的抽象。

## W1-Q9 事件循环的作用是什么？协程在什么时候让出执行权？

事件循环可以理解成 asyncio 的调度中心。

它会不停看：

哪些任务可以运行；

哪些任务在等 I/O；

哪些定时器到时间了；

哪些网络操作已经就绪。

协程并不是执行一会儿系统就强制把它切走。

它主要是在执行到 `await`，并且这个 await 的结果当前还没准备好的时候，把执行权交还给事件循环。

然后事件循环去跑别的任务。

所以如果我在 `async def` 里面写了一个特别重的计算循环，中间一个 await 都没有，那它还是会一直占着事件循环。

这也是为什么：

**async 不等于自动并发，真正关键的是有没有可让出的异步等待点。**

## W1-Q10 在 async def 中调用阻塞函数会发生什么？应该怎样处理？

这个问题在 FastAPI 里其实挺重要。

因为 `async def` 一般运行在事件循环线程里。

如果我在里面直接写：

`requests.get()`

或者：

`time.sleep(5)`

虽然函数名字是 async，但这段代码本身是阻塞的，它不会把执行权交还给事件循环。

结果就是这 5 秒不只是当前请求慢，其他协程也可能一起被拖慢。

所以我一般是先看有没有异步版本。

比如：

requests 换 httpx AsyncClient；

time.sleep 换 asyncio.sleep；

数据库换异步驱动。

如果确实有一个老的同步 I/O 库没法改，我可以用 `asyncio.to_thread()` 把它放线程池执行。

如果是 CPU 密集型任务，就不应该简单丢线程里，更多考虑多进程、任务队列或者独立服务。

## W1-Q11 asyncio.gather 和 TaskGroup 有什么主要区别？

我觉得两者都能解决“同时跑几个异步任务”的问题，但是设计思路不太一样。

`gather` 用起来比较直接。

比如我同时请求三个接口：

`await asyncio.gather(a(), b(), c())`

然后它把结果一次返回给我，而且结果顺序和传入顺序对应。

TaskGroup 更像把这些任务当成一个整体来管理。

比如这个业务里三个任务必须一起成功，其中一个失败了，那其他任务继续跑可能也没有意义。

TaskGroup 就会在一个任务失败的时候取消其他同组任务，并且退出作用域前统一处理。

所以我一般会这样选：

如果就是简单“并发跑几个任务，拿结果”，gather 很方便；

如果这些任务属于一个生命周期，希望失败和取消行为更统一，我更倾向 TaskGroup。

## W1-Q12 异步任务如何设置超时和正确处理取消？

外部服务调用我一般不会无限等。

比如调用模型服务，我可能只允许 10 秒。

可以通过 `asyncio.timeout()` 或 `wait_for()` 设置超时。

超时以后，底层任务通常会被取消。

取消时协程内部会收到 `CancelledError`。

这里我觉得最重要的是不要直接：

`except Exception: pass`

然后把所有异常都吞掉。

因为任务已经被要求取消了，如果我把取消异常吃掉，它可能还会继续跑，整个生命周期就乱了。

正确思路一般是：

如果占用了资源，就在 `finally` 中清理；

清理完成以后让取消继续向上传播。

所以我会记成：

**超时负责触发取消，finally 负责资源清理，不要随便吞 CancelledError。**

## W1-Q13 单线程协程为什么仍可能发生竞态条件？Lock 和 Semaphore 分别解决什么问题？

很多人会觉得 asyncio 是单线程，所以不可能有竞态，其实不是。

虽然同一时刻可能只有一个协程在执行 Python 代码，但是协程会在 await 的地方切换。

比如我先读取：

`stock = 10`

然后中间 await 一个数据库或者网络操作。

这时候另一个协程也可能读取到 stock=10。

最后两个任务都减 1，结果可能只变成 9，而不是 8。

所以只要一个共享状态的“读 → 改 → 写”过程跨越 await，就可能产生竞态。

Lock 是保证临界区同一时间只能有一个任务进入。

Semaphore 不一定只允许一个，它是限制最多 N 个并发。

比如第三方 API 限制最多 10 个并发请求，我就会用 Semaphore。

所以我会记成：

Lock 是保护共享状态；

Semaphore 是限制并发数量。

## W1-Q14 CPU 密集任务为什么不适合直接放在事件循环中？有哪些处理方式？

因为 CPU 密集任务的问题不是等待，而是一直在算。

事件循环最擅长的是：

这个任务等 I/O 的时候，我去跑别的任务。

但如果一个任务一直占 CPU，5 秒都没有 await，那事件循环也没机会切走。

所以一个 CPU 重任务就可能把整个 async 服务一起拖慢。

像图片处理、复杂 Python 计算、部分模型推理，我一般不会直接放在 FastAPI 的事件循环里。

处理方式可能有：

多进程；

ProcessPool；

Celery 这类任务队列；

独立推理服务；

或者把核心计算放到 C/C++、NumPy、PyTorch 这类原生实现里。

项目里我更倾向把 Web API 和重计算解耦，不让一个重任务占住所有在线请求。

## W1-Q15 FastAPI 依赖注入解决了什么问题？

我觉得 Depends 最核心的价值不是“少写几行代码”，而是把公共依赖和业务逻辑分开。

比如一个接口本来要做：

创建数据库 Session；

解析 Token；

获取当前用户；

检查权限；

然后才真正开始查数据。

如果这些逻辑全写在路由里，接口很快就会变得特别长。

用 Depends 以后，我可以把数据库、认证、权限这些东西单独拆出来。

路由只关心真正的业务。

还有一个我觉得很实用的地方是测试。

测试时我可以通过 `dependency_overrides`，把真实数据库或者认证依赖换成测试版本。

所以对我来说它主要解决：

**复用、解耦、资源管理和测试替换。**

## W1-Q16 Pydantic 校验和数据库约束有什么区别？

我会把它们理解成两道防线。

Pydantic 是第一道，在请求刚进入应用的时候就检查。

比如：

字段类型错了；

email 格式不对；

开始时间比结束时间还晚。

这种问题尽早拦掉，而且可以给客户端一个比较清楚的错误。

数据库约束是最后一道。

比如 UNIQUE、NOT NULL、FOREIGN KEY。

它不管请求是从 FastAPI 来的，还是有人直接执行 SQL，只要最终数据违反规则，数据库就不允许写进去。

所以关键规则不能只写 Pydantic。

例如用户名唯一，就算应用层先查了一次“用户名不存在”，两个并发请求还是可能同时通过检查。

最终还是数据库 UNIQUE 才能兜住。

所以我一般是：

**应用层负责友好校验，数据库负责最终一致性。**

## W1-Q17 ASGI 和 WSGI 有什么区别？为什么 FastAPI 通常运行在 ASGI 服务器上？

我一般先从应用场景理解。

WSGI 主要是为传统同步 Web 请求设计的。

一个请求进来，应用处理，然后返回响应。

ASGI 则增加了异步和事件驱动能力。

它除了普通 HTTP，还可以比较自然地处理 WebSocket、长连接、流式响应。

FastAPI 本身就是基于 ASGI 的，所以常见会跑在 Uvicorn 上。

像我做 LLM 流式输出的时候，需要 SSE；如果做实时双向通信，还可能用 WebSocket。

这些场景 ASGI 会更合适。

所以简单理解：

WSGI 偏同步请求响应；

ASGI 更适合现代异步 Web 服务和长连接场景。

## W1-Q18 FastAPI 路由应该使用 def 还是 async def？

我不会觉得 FastAPI 就一定全部写 `async def`。

我主要看下面调用的是什么。

如果我要调用 AsyncSession、异步 Redis、httpx AsyncClient，这些本身都支持 await，那就用 `async def`。

如果底层是一个同步阻塞库，用普通 `def` 反而可以，因为 FastAPI 会把同步路由放到线程池里处理。

最危险的是：

我写了 `async def`，然后里面调用 `requests`、`time.sleep` 或者同步数据库驱动。

表面看起来是异步接口，实际上把事件循环堵住了。

所以判断标准不是“async 看起来更高级”，而是：

**整个调用链是不是真的支持异步。**

## W1-Q19 中间件与依赖注入分别适合处理什么逻辑？

我一般看这个逻辑的作用范围。

如果几乎所有请求都要执行，我会先考虑 Middleware。

比如：

request_id；

请求耗时；

日志；

CORS；

统一 Header。

因为这些东西和具体业务接口关系不大，更像整个请求链路的公共逻辑。

Depends 更适合某一类接口需要的东西。

比如：

登录用户；

权限检查；

数据库 Session；

分页参数。

它可以明确写在路由参数里，而且还可以组合。

所以我的判断大概是：

全局横切逻辑用 Middleware；

路由级、可组合的业务依赖用 Depends。

## W1-Q20 FastAPI lifespan 适合管理哪些资源？为什么不应在每个请求中重复初始化？

lifespan 我一般会放应用级资源。

也就是说这个资源：

启动的时候创建一次；

整个应用运行期间反复复用；

关闭服务时再统一释放。

比如：

数据库连接池；

Redis Client；

HTTP Client；

Embedding 模型；

LLM Client。

假设一个模型加载需要 5 秒，我肯定不会每个请求来一次都重新 load model。

数据库连接池也是一样。

如果每次请求都创建新的池，不只是慢，还可能把数据库连接直接打满。

所以我一般会区分：

Session 是请求级资源；

连接池、客户端、模型通常是应用级资源。

lifespan 就比较适合管理后一类。

## W1-Q21 BackgroundTasks 适合做什么？为什么不能把它当作可靠任务队列？

BackgroundTasks 我一般只会拿来做一些比较轻的事情。

比如请求返回以后：

写日志；

发送一个不重要的通知；

做一点短时间清理。

它的优点就是简单。

但是它其实还是依附在当前 Web 进程里的。

如果服务正在执行任务时突然重启，那这个任务就可能直接没了。

它也没有完整的持久化、重试、任务状态、跨节点调度。

所以如果是：

模型推理；

批量发邮件；

视频处理；

重要的数据同步；

我一般不会用 BackgroundTasks 硬扛。

这种更适合 Celery、RQ 或者独立任务系统。

## W1-Q22 为什么要区分请求模型、数据库模型和响应模型？

这个我觉得本质上是在控制数据边界。

请求模型表示：

“客户端允许给我什么数据”。

数据库模型表示：

“系统内部到底怎么存”。

响应模型表示：

“我允许把什么东西返回给客户端”。

这三个其实不应该完全一样。

比如 User 数据库表里可能有：

password_hash；

is_deleted；

internal_note。

这些字段客户端不应该随便传，更不应该全部返回。

如果接口模型和 ORM 模型完全绑死，数据库表一改，API 很容易也被迫跟着改。

所以我会把它们分开，让 API 和数据库能够相对独立演进。

## W1-Q23 SSE 和 WebSocket 分别适合什么场景？

我先看通信是不是需要双向。

如果是 LLM 聊天：

用户先发一个问题；

服务器后面不断往前端推 token。

这种其实主要是服务器往客户端单向推。

所以 SSE 就很合适，而且它还是 HTTP，接入和排查都比较简单。

WebSocket 是真正的双向长连接。

客户端和服务器都可以随时发送消息。

像实时游戏、多人协作、聊天室这种双方都需要高频主动发送消息的场景，会更适合 WebSocket。

所以如果只是模型流式返回，我一般先选 SSE。

需要高频双向通信，再考虑 WebSocket。

## W1-Q24 为什么 AsyncSession 不应该在多个并发任务之间共享？

因为 AsyncSession 本身不是无状态的。

它里面会记录当前事务、当前连接，还有 ORM 对象状态。

如果我用：

`asyncio.gather()`

启动两个任务，然后把同一个 Session 传进去，就可能出现一个任务正在执行 SQL，另一个任务又 flush 或 commit。

两个任务的事务边界就混在一起了。

更严重一点，一个任务 rollback，可能把另一个任务的操作也一起影响。

所以我的原则是：

一个请求通常一个 Session；

如果请求内部还要真正并发执行多个数据库任务，那并发任务最好各自使用自己的 Session。

## W1-Q25 一个 Web 请求中的 SQLAlchemy Session 通常应如何创建、提交、回滚和关闭？

我一般通过 FastAPI 的 `yield` 依赖创建 Session。

请求进来以后创建一个 Session。

业务逻辑都使用这个 Session。

如果业务成功，在事务边界 commit。

如果中间出现异常，就 rollback。

不管成功失败，最后都要 close。

我比较在意的一点是：

不要每执行一次 SQL 就 commit。

因为一个业务操作可能包含多条 SQL，比如：

创建订单；

扣库存；

写支付记录。

它们应该属于一个事务。

所以 commit 应该跟着业务事务边界走，而不是跟着单条 SQL 走。

## W1-Q26 flush、commit 和 rollback 分别做什么？

flush 我一般理解成：

“先把 Session 里积攒的 SQL 发给数据库执行，但是事务先别提交。”

比如我新建一个 User，数据库主键是自动生成的。

执行 flush 以后，我通常就能拿到 user.id，但这时候如果后面 rollback，这条数据还是可以撤销。

commit 才是正式提交事务。

rollback 是撤销当前没提交的修改。

所以简单来说：

flush 是执行 SQL；

commit 是确认事务；

rollback 是出问题以后撤销。

## W1-Q27 数据库索引为什么能加速查询？索引是否越多越好？

索引我一般类比成书的目录。

没有索引的时候，数据库可能只能从头到尾扫表。

有合适索引以后，可以通过索引结构快速定位目标记录。

所以经常用在 WHERE、JOIN、ORDER BY 的字段通常值得关注。

但是索引不是越多越好。

因为数据插入、更新、删除的时候，不只是改表本身，还要同步维护索引。

索引太多以后写入会越来越慢，而且占空间。

所以实际项目里我不会看到字段就建索引。

我会根据：

真实查询语句；

字段选择性；

排序方式；

`EXPLAIN` 执行计划

来判断。

## W1-Q28 什么是 ORM 的 N+1 查询问题？怎样发现和解决？

比如我先查出 100 个 User。

这是第一次查询。

然后代码里写：

`for user in users:`
`    print(user.tasks)`

如果 tasks 是懒加载，那访问每个用户的时候可能都会再查一次数据库。

最后就是：

1 次查用户 + 100 次查 tasks。

总共 101 次查询。

这就是 N+1。

这种问题代码表面看起来特别正常，所以我一般会通过 SQL 日志、请求查询次数或者 APM 来发现。

解决方式就是不要一条一条懒加载。

可以用：

`selectinload`

`joinedload`

显式 Join

或者先批量查询。

核心就是：

**把循环里的数据库访问合并掉。**

## W1-Q29 Offset 分页和游标分页各有什么优缺点？

Offset 就是比较传统的：

第 1 页、第 2 页、第 100 页。

实现特别简单，而且用户可以直接跳页。

但问题是数据量大以后，比如：

`OFFSET 100000`

数据库可能需要先找到并跳过前面十万条数据，性能就会越来越差。

而且分页期间如果有数据插入或删除，还可能出现上一页和下一页有重复或者遗漏。

游标分页不是记“第几页”，而是记上一页最后一条记录。

比如：

`created_at < last_created_at`

然后继续往后查。

这样性能一般比较稳定。

所以我通常是：

后台管理系统、数据量不大，用 Offset 很方便；

聊天记录、Feed 流、大数据列表，我会更倾向游标分页。

## W1-Q30 数据库连接池耗尽通常有哪些原因？如何排查？

如果遇到 connection pool timeout，我不会马上就把 pool_size 从 10 改到 100。

因为很多时候根本原因不是池太小，而是连接被占住太久。

比如：

Session 没有关闭；

事务很长；

SQL 本身特别慢；

拿到连接以后又去调用一个 10 秒的外部 API；

请求量突然变大。

我会先看：

连接池正在使用多少连接；

等待连接的时间；

数据库里有哪些活跃事务；

有没有慢 SQL；

请求 trace 卡在哪一步。

然后再判断到底是：

连接泄漏；

SQL 太慢；

事务设计不合理；

还是流量确实已经超过容量。

先找原因，再决定是不是需要扩大连接池。

## W1-Q31 缓存与数据库数据不一致时，你会怎样处理？

这个我第一步不会先想 Redis 怎么改，我会先问自己：

这个数据到底允许多长时间不一致？

比如文章列表，晚几秒问题可能不大。

但如果是库存、余额，就不能这么随意。

普通业务我一般会用 Cache-Aside。

更新时先改数据库。

数据库成功以后删除缓存。

下一次请求缓存 miss，再去数据库读最新数据并回填。

另外缓存本身会设置 TTL，避免错误缓存永久存在。

如果删除缓存失败，我还需要有重试或者消息补偿。

所以我的核心原则是：

**数据库是真实数据源，Redis 是性能层，不应该反过来让缓存成为唯一真相。**

## W1-Q32 Cache-Aside 模式的基本读写流程是什么？

读的时候比较简单。

先 Redis。Redis 有，直接返回。Redis 没有，再查数据库。数据库查到以后写回 Redis。写的时候我一般不是“数据库改一次，Redis 也直接改一次”。因为两个系统很难保证完全原子。
更常见的做法是：先更新数据库；成功以后删除缓存。下一次请求自然会查数据库，然后重新写缓存。这样逻辑会简单很多。不过高并发场景下还是可能有竞态，所以如果一致性要求比较高，还可以加版本号、延迟双删或者消息同步。

## W1-Q33 缓存穿透、缓存击穿和缓存雪崩分别是什么？

我一般这样记，比较不容易混。

**穿透：查的数据根本不存在。**

Redis 没有，数据库也没有。

有人一直查 ID=-1，每次都穿过缓存打数据库。

解决可以用：

参数校验、缓存空值、布隆过滤器。

**击穿：一个热点 Key 突然没了。**

比如一个直播间热门数据刚好过期。

瞬间几万个请求一起去数据库重建。

解决可以用互斥锁、单飞、逻辑过期。

**雪崩：很多 Key 一起没了。**

比如大量缓存都设置 30 分钟 TTL，而且是同一时间写进去。

30 分钟以后一起过期。

这时候数据库一下承受大量请求。

一般会把 TTL 打散，加随机时间，再配合限流、降级。

## W1-Q34 使用 Redis 实现分布式锁时需要注意哪些问题？

Redis 分布式锁我主要关注几个问题。首先加锁要使用 `SET key value NX PX`，NX 是只有 Key 不存在才成功。PX 是设置过期时间，防止某个服务拿到锁以后挂了，锁永远不释放。保证加锁和设置过期时间是原子的，同时 value 要使用 UUID 之类的唯一标识。释放锁不能直接 DEL，而是要通过 Lua 脚本先判断锁是不是自己持有的，再原子删除，避免误删其他客户端的新锁。其次必须设置合理的 TTL，如果业务可能执行比较久，可以配合看门狗自动续期。另外获取锁失败时要做重试和退避，避免大量请求同时抢锁。对于核心业务，我不会只依赖 Redis 锁，还会通过数据库唯一约束、幂等设计等方式兜底。因为 Redis 主从切换、网络故障等情况下，单实例 Redis 锁并不能提供绝对的强一致性保证。

## W1-Q35 Redis 的 TTL 和内存淘汰策略有什么区别？常见数据结构怎样选择？ LRU = Least Recently Used，中文一般叫**最近最少使用淘汰策略**。LFU = Least Frequently Used，中文叫**最不经常使用淘汰策略**。

TTL 是我主动给一个 Key 设置：

“这个数据多久以后失效。”

比如用户缓存 5 分钟。

淘汰策略是另外一个概念。

Redis 内存到上限以后，需要主动腾空间，这时候决定“优先删谁”。

比如 LRU、LFU 这类策略。

数据结构我一般按操作需求选。

String 最常用，可以做缓存、计数器、幂等键。

Hash 比较适合一个对象的多个字段。

Set 适合去重和集合关系。

Sorted Set 适合排行榜这种“既要唯一又要排序”。

Stream 更适合事件流或者轻量消息场景。

我一般不会为了用 Redis 数据结构而用，而是先看业务要做什么操作。

## W1-Q36 单元测试和集成测试有什么区别？本项目各测什么？

我一般先区分测试目标。

单元测试问的是：

“这个函数自己有没有问题？”

所以我会尽量把数据库、Redis、外部 API 隔离掉。

比如测试：

参数校验；

业务规则；

计算逻辑；

工具函数。

它最大的好处是快，而且失败以后定位很准。

集成测试问的是：

“这些模块真正连起来还能不能工作？”

比如调用一个 FastAPI 接口：

数据库真的插入了吗？

Redis 有没有写缓存？

事务失败时有没有 rollback？

所以项目里两种都会有。

单元测试保证局部逻辑；

集成测试保证链路真的能跑通。

## W1-Q37 pytest fixture、mock 和 FastAPI dependency_overrides 分别适合解决什么问题？

fixture 我主要拿来准备测试环境。

比如：

测试客户端；

临时数据库 Session；

测试用户；

测试数据。

而且测试结束以后，它还可以统一负责清理。

mock 更多是替换外部边界。

比如测试用户注册，我不想真的发邮件，就把 send_email mock 掉。

然后还可以检查它有没有被调用一次。

`dependency_overrides` 是 FastAPI 特别方便的地方。

比如路由里依赖：

`get_db`

`get_current_user`

测试时可以直接把这些依赖替换成测试版本。

所以我一般不会混着用。

fixture 管环境；

mock 管普通函数或外部调用；

dependency_overrides 管 FastAPI Depends。

## W1-Q38 涉及数据库的自动化测试怎样保证用例相互隔离？

数据库测试首先保证测试隔离。简单场景下，我会让每个测试使用独立的 Session 和事务，测试结束统一回滚；测试数据中的唯一字段会使用 UUID 等方式生成，避免并发冲突。对于跨连接、异步任务或者集成测试这类复杂场景，则进一步使用独立测试数据库或独立 Schema，避免测试之间共享状态。

## W1-Q39 Docker 镜像和容器有什么区别？Dockerfile 与 Compose 分别负责什么？

这个我一般会类比一下。

镜像更像一个安装好的系统模板。

里面已经定义了：

Python 版本；

依赖；

应用代码；

启动命令。

但它本身不是一个正在运行的服务。

容器是把这个镜像真正启动起来以后的运行实例。

同一个镜像可以启动多个容器。

Dockerfile 负责的是：

**单个镜像怎么构建出来。**

Compose 负责的是：

**整个项目里的多个服务怎么一起运行。**

比如我的项目有：

FastAPI；

PostgreSQL；

Redis。

Dockerfile 管 FastAPI 镜像怎么做。

docker-compose.yml 管这三个服务的端口、网络、环境变量、Volume 和依赖关系。

## W1-Q40 一个 FastAPI 接口突然变慢，你会按什么顺序排查？

这个我一般不会一上来就“优化代码”，因为首先得确认到底是谁慢。

我会先看监控或者日志。

第一步确认：

是不是所有接口都慢，还是只有某一个接口慢。

然后看：

是首字节时间变长，还是流式输出过程中变慢。

接下来我会沿着 request_id 或 trace 把请求拆开。

看每一层时间：

路由逻辑；

数据库；

Redis；

外部 API；

LLM 或模型服务。

如果数据库占了大头，我就继续查：

慢 SQL；

索引；

执行计划；

锁等待；

连接池等待。

如果整个服务突然一起慢，我会怀疑：

事件循环是不是被阻塞；

是不是 CPU 打满；

是不是内存或者连接数出问题。

然后还会看最近有没有部署新版本，因为很多性能问题都是某次改动以后出现的。

等瓶颈定位以后，再针对那个位置优化。

最后还要通过压测或者线上指标确认：

**到底是真的变快了，还是只是感觉变快了。**

所以我整个排查思路是：

**先定位范围 → 再拆链路 → 找真正瓶颈 → 修复 → 用数据验证。**
