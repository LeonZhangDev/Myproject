# 大模型生成内容附带来源地址的实现方案

## 1. 目标

目标是让大模型在生成回答时，同时给出真实、可点击、可追踪的来源地址。

例如：

```text
成都大熊猫繁育研究基地适合安排半天游览。[1]
```

其中 `[1]` 对应：

```json
{
  "id": 1,
  "title": "成都大熊猫繁育研究基地游客指南",
  "url": "https://example.com/panda",
  "source_id": "source_001"
}
```

核心原则：

> URL 不让大模型自己生成，而是由系统提前保存，并在检索后与回答中的引用编号进行绑定。

---

# 2. 方案一：Prompt Citation

## 2.1 原理

最简单的方式是在 Prompt 中要求模型：

```text
回答问题，并在答案中附上来源链接。
```

例如：

```text
请根据下面资料回答问题。

回答时：
1. 只能使用资料中的内容。
2. 每个事实后面附上来源 URL。
3. 不允许编造链接。
```

---

## 2.2 实现方式

检索到的内容直接放入 Prompt：

```text
Source 1:
成都大熊猫繁育研究基地位于成都。

URL:
https://example.com/panda
```

模型直接输出：

```text
成都大熊猫繁育研究基地位于成都。
来源：https://example.com/panda
```

---

## 2.3 后端流程

```text
Query
  ↓
Retriever
  ↓
Top-K Documents
  ↓
把 text + URL 一起放入 Prompt
  ↓
LLM
  ↓
Answer + URL
```

---

## 2.4 优点

- 实现最快
- 几乎不需要修改现有 RAG
- 适合快速 Demo

---

## 2.5 缺点

最大问题是：

> 模型仍然可以修改、遗漏或者编造 URL。

因此不适合作为正式生产方案。

---

# 3. 方案二：Generation-Time Citation

这是最推荐作为第一版正式实现的方案。

---

## 3.1 原理

URL 不交给模型。

模型只看到：

```text
[Source 1]
成都大熊猫繁育研究基地位于成都……

[Source 2]
宽窄巷子是成都历史文化街区……
```

然后要求模型：

```text
每个事实后必须使用 [1]、[2] 这样的引用编号。
```

模型输出：

```text
成都大熊猫繁育研究基地是成都重要旅游景点之一。[1]

宽窄巷子具有明显的历史文化特色。[2]
```

真正的 URL 由后端保存：

```text
1 → https://example.com/panda
2 → https://example.com/kuanzhai
```

---

# 4. Generation-Time Citation 具体怎么实现

## 4.1 第一步：文档入库时保存来源信息

LlamaIndex Document 建议保存：

```python
Document(
    text=content,
    metadata={
        "source_id": "source_001",
        "title": "成都熊猫基地游客指南",
        "url": "https://example.com/panda",
        "domain": "example.com",
        "document_id": "doc_001"
    }
)
```

切 Chunk 后继续保留：

```text
source_id
title
url
document_id
chunk_id
```

最终每个 Node 都应该类似：

```python
{
    "text": "...",
    "metadata": {
        "source_id": "source_001",
        "title": "成都熊猫基地游客指南",
        "url": "https://example.com/panda",
        "document_id": "doc_001",
        "chunk_id": "doc_001_chunk_03"
    }
}
```

---

## 4.2 第二步：Retriever 不要只返回文本

不要这样：

```python
contexts = [node.text for node in nodes]
```

应该构造 Evidence：

```python
evidence_list = []

for index, node in enumerate(nodes, start=1):
    evidence_list.append({
        "citation_id": index,
        "text": node.text,
        "score": node.score,
        "source_id": node.metadata["source_id"],
        "title": node.metadata["title"],
        "url": node.metadata["url"],
        "chunk_id": node.metadata["chunk_id"],
    })
```

这样：

```text
Evidence
├── citation_id
├── text
├── score
├── source_id
├── title
├── url
└── chunk_id
```

一直保留到最后。

---

## 4.3 第三步：生成 Citation Context

把检索结果转成：

```text
[Source 1]
成都大熊猫繁育研究基地主要承担大熊猫繁育、科研和公众教育工作。

[Source 2]
宽窄巷子由宽巷子、窄巷子和井巷子组成。
```

注意：

> 不需要把 URL 发给模型。

---

## 4.4 第四步：修改生成 Prompt

推荐：

```text
你只能根据提供的 Evidence 回答。

规则：

1. 任何事实性陈述后面都必须附上 Citation。
2. Citation 格式只能是 [1]、[2]、[3]。
3. 一个事实可以使用多个 Citation，例如 [1][3]。
4. 不允许使用没有提供的 Citation ID。
5. 不允许自己生成 URL。
6. 如果证据不足，请明确说明证据不足。
```

---

## 4.5 第五步：模型生成

例如：

```text
成都大熊猫繁育研究基地主要承担大熊猫繁育、
科研和公众教育工作。[1]

宽窄巷子由多个传统街巷组成。[2]
```

---

## 4.6 第六步：后端解析 Citation

可以用正则：

```python
import re

citation_ids = re.findall(r"\[(\d+)\]", answer)
```

例如：

```text
answer:

成都大熊猫繁育研究基地……[1]
```

得到：

```python
["1"]
```

然后去：

```python
evidence_list
```

寻找：

```text
citation_id = 1
```

---

## 4.7 第七步：返回结构化 Citation

FastAPI 不要只返回：

```json
{
  "answer": "成都熊猫基地……[1]"
}
```

而应该返回：

```json
{
  "answer": "成都熊猫基地……[1]",
  "citations": [
    {
      "citation_id": 1,
      "source_id": "source_001",
      "title": "成都熊猫基地游客指南",
      "url": "https://example.com/panda",
      "chunk_id": "doc_001_chunk_03"
    }
  ]
}
```

---

## 4.8 第八步：前端绑定

前端拿到：

```text
[1]
```

之后寻找：

```text
citations[1]
```

然后显示：

```text
[1] 成都熊猫基地游客指南
```

用户点击：

```text
https://example.com/panda
```

即可打开真实页面。

# 5. 方案三：Post-hoc Citation

## 5.1 原理

这种方案不是让模型边生成答案边引用。

而是：

```text
先生成答案
    ↓
把答案拆成 Claim
    ↓
针对每个 Claim 搜索证据
    ↓
给 Claim 补 Citation
```

例如第一阶段生成：

```text
成都熊猫基地主要负责大熊猫科研工作。

宽窄巷子属于成都历史文化街区。
```

然后拆成：

```text
Claim 1:
成都熊猫基地主要负责大熊猫科研工作。

Claim 2:
宽窄巷子属于成都历史文化街区。
```

再分别检索：

```text
Claim 1 → Evidence 3
Claim 2 → Evidence 7
```

最终：

```text
成都熊猫基地主要负责大熊猫科研工作。[1]

宽窄巷子属于成都历史文化街区。[2]
```

---

# 6. Post-hoc Citation 具体怎么实现

## 6.1 第一步：正常生成答案

```text
Query
 ↓
RAG
 ↓
LLM
 ↓
Answer
```

暂时不要求引用。

---

## 6.2 第二步：拆 Atomic Claim

例如：

```text
成都春季温度较舒适，而且成都熊猫基地上午游客较多。
```

拆成：

```json
[
  "成都春季温度较舒适。",
  "成都熊猫基地上午游客较多。"
]
```

可以使用 LLM：

```text
请把下面回答拆成最小的、可以独立验证真假的事实声明。
```

---

## 6.3 第三步：每个 Claim 单独检索

例如：

```python
for claim in claims:
    nodes = retriever.retrieve(claim)
```

得到：

```text
Claim 1
 ↓
Top-K Evidence

Claim 2
 ↓
Top-K Evidence
```

---

## 6.4 第四步：选择支持 Claim 的 Evidence

可以先使用：

```text
Embedding Similarity
+
Reranker
```

之后再使用：

```text
LLM Judge
```

判断：

```text
SUPPORTED
UNSUPPORTED
CONTRADICTED
```

---

## 6.5 第五步：绑定 Citation

例如：

```text
Claim 1 → Source 2
Claim 2 → Source 5
```

最终拼成：

```text
成都春季温度较舒适。[1]

成都熊猫基地上午游客较多。[2]
```

---

## 6.6 优点

- Citation Coverage 通常更高
- 可以对每个 Claim 单独查证
- 更适合长回答
- 更容易做 Citation Verification

---

## 6.7 缺点

需要额外：

```text
Claim Extraction
+
Retrieval
+
Verification
```

所以：

- 延迟更高
- Token 成本更高
- 工程复杂度更高

---

# 7. 方案四：Hybrid Verified Citation

这是最终最推荐的完整方案。

它把：

```text
Generation-Time Citation
```

和：

```text
Post-hoc Verification
```

组合起来。

整体流程：

```text
Query
  ↓
Retriever
  ↓
Reranker
  ↓
Top-K Evidence
  ↓
LLM 生成 Answer + [1][2]
  ↓
Claim Extraction
  ↓
检查 Claim 与 Citation 是否一致
  ↓
SUPPORTED?
  ├── Yes → 保留
  └── No
       ↓
    重新检索
       ↓
    找新的 Evidence
       ↓
    Rewrite / Remove / Abstain
```

---

# 8. Hybrid Verified Citation 具体怎么实现

## 8.1 第一阶段：正常 Citation RAG

先使用方案二：

```text
Retriever
 ↓
Evidence
 ↓
编号 Source
 ↓
LLM
 ↓
Answer + [1][2]
```

例如：

```text
九寨沟属于高原湿润气候。[1]

九寨沟全年平均温度为 15℃。[2]
```

---

## 8.2 第二阶段：提取 Claim

变成：

```json
[
  {
    "claim": "九寨沟属于高原湿润气候。",
    "citations": [1]
  },
  {
    "claim": "九寨沟全年平均温度为15℃。",
    "citations": [2]
  }
]
```

---

## 8.3 第三阶段：Citation Verifier

检查：

```text
Claim
+
Citation 对应的 Evidence
```

例如：

```text
Claim:
九寨沟全年平均温度为 15℃。

Evidence:
九寨沟属于高原湿润气候。
```

让 Judge 返回：

```text
SUPPORTED
PARTIALLY_SUPPORTED
UNSUPPORTED
CONTRADICTED
```

---

## 8.4 第四阶段：处理错误 Citation

### SUPPORTED

```text
直接保留
```

### PARTIALLY_SUPPORTED

尝试：

```text
增加第二条 Evidence
```

### UNSUPPORTED

执行：

```text
Claim
 ↓
重新检索
 ↓
Reranker
 ↓
寻找新的 Evidence
```

如果找到了：

```text
替换 Citation
```

如果仍然没有：

```text
删除 Claim
```

或者：

```text
现有资料不足以确认这一信息。
```

### CONTRADICTED

优先：

```text
删除 / 重写 Claim
```

---

# 9. Citation Verifier 怎么实现

第一版可以直接使用 LLM Judge。

Prompt：

```text
你需要判断 Evidence 是否支持 Claim。

Claim:
{claim}

Evidence:
{evidence}

只能输出下面四种结果之一：

SUPPORTED
PARTIALLY_SUPPORTED
UNSUPPORTED
CONTRADICTED
```

以后再考虑换成 NLI 模型。

逻辑本质上是：

\[
$$
P(\text{entailment} \mid Evidence, Claim)
$$
\]

# 10. SSE 流式接口怎么实现

如果当前 FastAPI 使用 SSE，建议不要让 Citation URL 跟着 Token 一起流。

推荐：

```text
event: text_delta
data: 成都熊猫基地适合安排半天。[1]
```

模型回答结束后：

```text
event: citations
data:
[
  {
    "id": 1,
    "title": "成都熊猫基地游客指南",
    "url": "https://example.com/panda"
  }
]
```

最后：

```text
event: done
```

也就是：

```text
先流 Answer
   ↓
Answer 完成
   ↓
返回 Citations Metadata
```

这样最简单稳定。

# 11. 推荐统一的数据结构

建议后端统一使用：

```json
{
  "answer": "成都熊猫基地适合安排半天游览。[1]",
  "citations": [
    {
      "citation_id": 1,
      "source_id": "source_001",
      "document_id": "doc_001",
      "chunk_id": "doc_001_chunk_03",
      "title": "成都熊猫基地游客指南",
      "url": "https://example.com/panda",
      "retrieval_score": 0.86,
      "reranker_score": 0.93
    }
  ]
}
```

这样：

```text
LLM
只负责 citation_id

Backend
负责 citation_id → URL

Frontend
负责 citation_id → UI
```

三个职责完全分开。

# 12. 四种方案对比

## 方案一：Prompt Citation

流程：

```text
Text + URL
 ↓
LLM
 ↓
Answer + URL
```

适合：

```text
Demo
```

不推荐生产使用。

---

## 方案二：Generation-Time Citation

流程：

```text
Evidence
 ↓
编号
 ↓
LLM
 ↓
Answer + [1]
 ↓
Backend Mapping
 ↓
真实 URL
```

适合：

```text
第一版正式 Citation RAG
```

推荐优先实现。

---

## 方案三：Post-hoc Citation

流程：

```text
Answer
 ↓
Claim Extraction
 ↓
Claim Retrieval
 ↓
Citation Matching
```

适合：

```text
长文本
Research Agent
高 Citation Coverage 场景
```

---

## 方案四：Hybrid Verified Citation

流程：

```text
Generation-Time Citation
         +
Claim Verification
         +
Re-Retrieval
```

适合：

```text
最终生产版本
高可靠 RAG
```

是完整方案中最推荐的。

# 13. 对当前项目的推荐实施顺序

当前最合理的路线不是一次性实现全部功能。

建议：

## V1

实现：

```text
Document Metadata
      ↓
Retriever 保留 Metadata
      ↓
Evidence 编号
      ↓
Prompt Citation
      ↓
Answer + [1]
      ↓
Citation JSON
      ↓
前端可点击来源
```

也就是：

> Generation-Time Citation

这是第一阶段最应该完成的。

---

## V2

增加：

```text
Atomic Claim Extraction
        ↓
Citation Verification
```

也就是检查：

```text
这个 [1]
到底能不能支持前面的 Claim
```

---

## V3

增加：

```text
Unsupported Claim
      ↓
Re-Retrieval
      ↓
Rewrite / Remove
```

形成：

> Hybrid Verified Citation

---

# 14. 最终推荐

如果只选一种最终技术路线：

```text
LlamaIndex Retrieval
        ↓
BGE Reranker
        ↓
Top-K Evidence
        ↓
Evidence Metadata
        ↓
Source 编号
        ↓
LLM 生成 Answer + [1][2]
        ↓
Citation Parser
        ↓
Claim-level Citation Verifier
        ↓
失败则 Re-Retrieval
        ↓
Citation Mapper
        ↓
FastAPI SSE
        ↓
Frontend
```

最重要的设计原则可以概括成三句话：

> **URL 由系统保存，不由模型生成。**

> **LLM 只选择 Citation ID。**

> **Citation 是否真的支持 Claim，再由 Verifier 检查。**

对于当前 LlamaIndex + FastAPI 架构，建议先实现 **Generation-Time Citation**，再逐步升级成 **Hybrid Verified Citation**。
