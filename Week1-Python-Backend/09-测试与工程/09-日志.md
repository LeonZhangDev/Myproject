# 日志

## 一句话理解

日志是问题发生后还原行为的证据。

## 核心理解

至少要有时间、级别、request_id、路径、耗时、错误。

## 🧠 完整理解

### 我会先这样理解

日志是运行时事实记录，不是 `print` 的升级版。工程日志需要级别、结构化字段、时间、模块、request-id，并区分哪些信息适合 DEBUG/INFO/WARNING/ERROR。好的日志应该帮助回答“哪一个请求、在哪一步、因为哪个依赖、发生了什么”，同时避免泄露 token、密码、个人信息。

### 执行顺序 / 思考顺序

请求进入生成上下文字段 → 各层日志都携带 request-id/user/task 等关键维度 → 日志输出到 stdout/collector → ELK/Loki/云日志聚合 → 通过字段检索还原一次请求链路。异常日志记录 stack trace。

### 容易踩的坑

不要一遇到异常就在每一层都 `logger.exception`，会重复刷同一堆栈。也不要把大模型完整 prompt、Authorization、数据库密码无脱敏写日志。

### 面试时我会这样说

> 我写日志会想象线上半夜只剩这些日志能救我。所以不能只写“error occurred”，至少要有 request-id、关键业务 id、异常堆栈。敏感字段一定脱敏，日志太多同样会淹没问题。

## 最小代码 / 场景

```text
2026-... INFO request_id=... path=/tasks duration_ms=34
```


## 🧪 简单例子与返回结果

### 例子

```python
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)
logger.info("user_id=%s login success", 42)
```

### 运行 / 返回结果

```text
INFO:__main__:user_id=42 login success
```
