# 集成测试

## 一句话理解

验证 API、DB、Redis 等真实协作。

## 核心理解

关键接口、事务和缓存行为应有集成测试。

## 🧠 完整理解

### 我会先这样理解

集成测试验证多个真实组件组合后能否正常工作，例如 FastAPI + SQLAlchemy + PostgreSQL、Redis 缓存链路。它比单测慢，但能发现 SQL 方言、事务、序列化、依赖配置等 mock 无法覆盖的问题。工程上通常用测试容器或独立测试数据库，并保证数据隔离和可重复。

### 执行顺序 / 思考顺序

启动测试依赖 → 准备 schema/fixture → 通过 HTTP/TestClient 或 service 调用真实组件 → 数据库/Redis 执行 → 验证响应和持久状态 → 清理事务/容器。

### 容易踩的坑

不要让集成测试连接开发或生产数据库；测试之间共享脏数据会导致顺序依赖和偶发失败。也别把所有测试都做成集成测试，否则 CI 会又慢又难定位。

### 面试时我会这样说

> 我会用单测守业务逻辑，用集成测试守组件边界。比如 ORM 查询是不是实际能在 PostgreSQL 跑、事务 rollback 是否正确，这种就应该连真实测试库验证，而不是只 mock Session。

## 最小代码 / 场景

```text
HTTP -> FastAPI -> SQLAlchemy -> Test DB
```


## 🧪 简单例子与返回结果

### 例子

```python
from fastapi.testclient import TestClient

client = TestClient(app)

def test_ping():
    r = client.get("/ping")
    assert r.status_code == 200
    assert r.json() == {"pong": True}
```

### 运行 / 返回结果

```text
pytest 运行：
1 passed
```

**怎么理解：** 这里同时经过了 FastAPI 路由、请求处理和响应序列化，比只测一个普通函数更接近集成测试。
