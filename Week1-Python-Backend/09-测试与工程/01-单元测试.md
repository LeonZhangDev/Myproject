# 单元测试

## 一句话理解

隔离一个函数/服务/工具，快且定位精确。

## 核心理解

适合纯业务逻辑、校验、工具函数。

## 🧠 完整理解

### 我会先这样理解

单元测试关注一个相对小的行为单元，尽量隔离数据库、网络等外部依赖，验证输入、输出和边界逻辑。它的价值是反馈快、定位准，适合覆盖纯业务规则和工具函数。好的单测不是“为了覆盖率把每行跑一遍”，而是围绕行为和容易出错的边界建立保护网。

### 执行顺序 / 思考顺序

Arrange 准备输入/依赖 → Act 调被测单元 → Assert 验证结果、异常或副作用 → 每个 case 独立运行。外部依赖通过 fake/mock 注入，避免测试因为网络或数据库波动变慢。

### 容易踩的坑

过度 mock 实现细节会让重构很痛苦：代码行为没变，但测试全坏。单测更应该断言公开行为，而不是内部调用次数，除非调用本身就是契约。

### 面试时我会这样说

> 我写单测会尽量让它快而且失败原因明确。比如计算订单总价这种纯逻辑就很适合单测；真正数据库 JOIN 是否正确，我不会硬 mock，而会放到集成测试验证。

## 最小代码 / 场景

```python
def test_add(): assert add(1,2)==3
```


## 🧪 简单例子与返回结果

### 例子

```python
def add(a, b):
    return a + b

def test_add():
    assert add(2, 3) == 5
```

### 运行 / 返回结果

```text
pytest 运行：
1 passed
```
