# Redis 分布式锁

## 一句话理解

协调多个进程/机器对同一资源的互斥访问。

## 核心理解

需要原子加锁、过期、唯一 token、安全释放、长任务续期；不能替代幂等/唯一约束。

## 🧠 完整理解

### 我会先这样理解

分布式锁用于多个进程/实例共同竞争某个跨机器临界资源。Redis 锁常见思路是 `SET key token NX PX ttl` 原子抢锁，释放时只删除“token 仍属于自己”的锁。TTL 用来避免持锁实例崩溃后永久死锁，但也带来锁提前过期的问题。

### 执行顺序 / 思考顺序

实例 A SET NX PX 成功 → 进入临界区 → B/C 抢锁失败等待或退出 → A 完成后用 token 校验 + DEL 原子释放。若 A 崩溃，TTL 到期后锁自动释放，其他实例才有机会继续。

### 容易踩的坑

分布式锁不是强一致万能工具。任务执行时间超过 TTL 时可能出现两个持有者；网络分区、Redis 故障、续租都要考虑。对库存扣减等问题，数据库条件更新可能比外置锁更直接。

### 面试时我会这样说

> 我用 Redis 锁时至少会保证三件事：SET NX PX 一条命令抢锁、value 放随机 token、释放用 Lua 校验 token 再删。然后我还会问业务能不能接受锁过期，如果不能，就要续租或换更合适的一致性方案。

## 最小代码 / 场景

```redis
SET lock:task:1 token-abc NX PX 10000
```


## 🧪 简单例子与返回结果

### 例子

```text
服务 A：SET lock:job tokenA NX PX 10000 -> 成功
服务 B：SET lock:job tokenB NX PX 10000 -> 失败
```

### 运行 / 返回结果

```text
A 获得锁并执行临界任务；
B 此时不能同时进入，避免多个实例重复执行同一任务。
```
