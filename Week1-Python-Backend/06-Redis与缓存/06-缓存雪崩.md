# 缓存雪崩

## 一句话理解

大量 Key 同时失效导致大规模回源。

## 核心理解

TTL 打散、分批预热、限流、降级。

## 🧠 完整理解

### 我会先这样理解

缓存雪崩指大量 key 在相近时间同时失效，或者 Redis 整体不可用，导致原本由缓存吸收的流量突然集中打向数据库/下游。它是系统级问题，不是单个 key 热点。常见手段包括 TTL 加随机抖动、多级缓存、Redis 高可用、限流/熔断和数据库保护。

### 执行顺序 / 思考顺序

正常情况下流量大部分 Redis hit → 大批 TTL 同时到期或 Redis 故障 → miss 比例瞬间升高 → DB QPS 暴涨 → DB 变慢又导致请求堆积 → 可能形成级联故障。防护目标是打散失效和限制回源。

### 容易踩的坑

只给 TTL 加随机数不能解决 Redis 整体宕机；高可用也不能替代限流和降级。真正稳定的系统需要多层防线。

### 面试时我会这样说

> 我会把雪崩看成“缓存这一层突然大面积失效”。单纯随机 TTL 只能解决集中到期，Redis 整体挂了还要靠主从/集群、限流、熔断和降级，避免数据库也跟着被打死。

## 最小代码 / 场景

```text
TTL = base + random_jitter
```


## 🧪 简单例子与返回结果

### 例子

```text
10000 个 key 都设置相同 TTL=300 秒
```

### 运行 / 返回结果

```text
300 秒左右大量 key 同时过期 -> DB 瞬间承压
改为 TTL=300 + 随机抖动，可把过期时间打散。
```
