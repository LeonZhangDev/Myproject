# 幂等键

## 一句话理解

识别重复请求，让重复提交不重复产生副作用。

## 核心理解

关键唯一性仍要数据库约束兜底。

## 🧠 完整理解

### 我会先这样理解

幂等键用来保证同一个业务请求重复提交时只产生一次核心副作用。客户端生成 request_id/idempotency-key，服务端用 Redis/数据库记录处理状态或最终结果。它常用于支付、下单、任务提交等重试不可避免的接口。重点是幂等范围、过期时间和并发原子性。

### 执行顺序 / 思考顺序

请求携带幂等 key → 服务端原子检查/占位 → 第一个请求进入业务处理 → 成功后保存结果或状态 → 重复请求发现 key 已存在 → 直接返回已有结果/处理中状态，而不是再次执行副作用。

### 容易踩的坑

简单 `GET` 再 `SET` 不是原子的，两个并发请求仍可能同时通过；应使用 SET NX、数据库 UNIQUE 等原子机制。幂等 key 也要绑定用户/接口/业务参数，避免错误复用。

### 面试时我会这样说

> 我把幂等理解成“同一个业务动作重放很多次，最终效果还是一次”。实现时关键不是先查 Redis 再 set，而是第一个占位动作必须原子，常用 SET NX 或数据库唯一键。

## 最小代码 / 场景

```redis
SET idem:order:abc 1 NX EX 300
```


## 🧪 简单例子与返回结果

### 例子

```text
请求携带 Idempotency-Key: order-abc
服务先执行 SET order-abc processing NX EX 60
```

### 运行 / 返回结果

```text
第一次请求：SET 成功 -> 创建订单
重复请求：SET 失败 -> 不再重复创建订单
```
