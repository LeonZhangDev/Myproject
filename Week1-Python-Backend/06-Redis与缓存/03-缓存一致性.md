# 缓存一致性

## 一句话理解

缓存是数据库副本，更新不同步就会读旧数据。

## 核心理解

常见：Cache-Aside、写后失效、TTL、版本号、消息/CDC、删除失败重试。

## 🧠 完整理解

### 我会先这样理解

缓存一致性问题来自“同一份业务数据在数据库和缓存里有两个副本”。只要更新不是一个原子事务，就会存在短暂或异常情况下的不一致。设计时先明确一致性目标：允许几十秒最终一致，还是余额/库存这类不能读旧值。不同目标对应 TTL、删缓存、消息同步、版本号等不同方案。

### 执行顺序 / 思考顺序

写请求修改事实源 DB → 缓存副本需要失效或更新 → 中间任一步失败/并发读写交错都可能产生窗口 → 通过重试、TTL、消息/CDC、版本检查逐步收敛到最新状态。

### 容易踩的坑

不要把“延迟双删”当万能强一致方案。复杂系统里要讨论失败重试、消息丢失、乱序和幂等。强一致需求有时应该干脆绕过缓存或改变数据模型。

### 面试时我会这样说

> 我聊缓存一致性会先问“业务能接受多旧”。如果允许几秒最终一致，DB 更新后删缓存 + TTL 往往够；如果是余额这种强约束，我不会只靠缓存技巧硬凑，而会让数据库或专门的一致性方案做主。

## 最小代码 / 场景

```text
UPDATE DB -> COMMIT -> DELETE CACHE
```


## 🧪 简单例子与返回结果

### 例子

```text
更新用户昵称：
1. UPDATE users SET name='Leon' WHERE id=1
2. DEL user:1
```

### 运行 / 返回结果

```text
下一次读取 user:1：缓存 miss
-> 重新查数据库得到 Leon
-> 写回最新缓存
```

**怎么理解：** 常见 Cache-Aside 更新策略是“先更新数据库，再删除缓存”。
