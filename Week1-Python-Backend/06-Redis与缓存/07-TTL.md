# TTL

## 一句话理解

TTL 决定某个 Key 什么时候过期。

## 核心理解

它不同于内存达到上限时“删谁”的淘汰策略。

## 🧠 完整理解

### 我会先这样理解

TTL 是缓存条目的生命周期边界，用于自动淘汰陈旧数据和控制内存。TTL 长意味着命中率高但旧数据窗口更长，TTL 短则一致性更好但回源更多。实际设计通常按数据变化频率、热点程度和业务可接受陈旧度选择，还会加随机抖动防止集中失效。

### 执行顺序 / 思考顺序

SET key EX/PEX → Redis 记录过期时间 → 读取时可能触发惰性删除，同时后台也会周期清理过期 key → TTL 到点后 key 不再可用 → 下一次请求回源重建。

### 容易踩的坑

过期删除不是保证在某个毫秒物理内存立刻释放，而是语义上 key 过期不可见并由 Redis 回收。没有 TTL 的缓存 key 需要明确淘汰策略，避免长期积累。

### 面试时我会这样说

> 我不会所有缓存统一写 300 秒。配置 TTL 时会看数据多久变化一次、能接受多旧、回源成本多高；大批同类 key 还会加一点随机值，避免同一秒集体过期。

## 最小代码 / 场景

```redis
SET task:1 value EX 300
TTL task:1
```


## 🧪 简单例子与返回结果

### 例子

```bash
redis-cli SET session:1 abc EX 60
redis-cli GET session:1
```

### 运行 / 返回结果

```text
OK
"abc"

60 秒后再次 GET：
(nil)
```
