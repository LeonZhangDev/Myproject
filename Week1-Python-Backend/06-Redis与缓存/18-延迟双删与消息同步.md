# 延迟双删与消息同步

## 一句话理解

高并发下可用二次删除、消息或 CDC 修复短暂不一致。

## 核心理解

复杂方案只在一致性要求确实需要时使用。

## 🧠 完整理解

### 我会先这样理解

延迟双删和消息同步都是降低缓存脏数据窗口的手段。延迟双删通常在数据库更新前后删除缓存，并在短延迟后再删一次，试图清掉并发旧读回填的脏缓存；消息/CDC 同步则在数据库变化后通过可靠事件通知缓存失效。后者更适合大型系统，但需要处理消息丢失、重复和乱序。

### 执行顺序 / 思考顺序

并发读可能在写事务期间读到旧 DB 值并回填缓存 → 写请求提交新值并删缓存 → 若时序不巧旧回填发生在删除之后，就留下脏值 → 延迟再删或订阅数据库变更事件可以再次失效并最终收敛。

### 容易踩的坑

延迟时间没有一个“数学上永远正确”的固定值，因此它不是严格强一致。消息同步必须有重试、幂等、监控和补偿，否则只是把一致性问题从缓存搬到消息链路。

### 面试时我会这样说

> 我会把延迟双删看成一种工程补偿，不会说它保证强一致。系统复杂以后我更倾向于让 DB 变更通过消息/CDC 驱动缓存失效，但这时又要认真处理消息可靠性和幂等。

## 最小代码 / 场景

```text
DB change -> binlog/CDC/event -> consumer -> invalidate cache
```


## 🧪 简单例子与返回结果

### 例子

```text
更新 user:1：
1. DEL user:1
2. UPDATE DB
3. 延迟一小段时间后再次 DEL user:1
```

### 运行 / 返回结果

```text
即使并发读在更新窗口里把旧值写回缓存，第二次 DEL 也会再次清理它。
下一次读取重新从 DB 获取新值。
```
