# 连接池

## 一句话理解

复用数据库连接，避免每请求都重新建立连接。

## 核心理解

耗尽常见原因：Session 泄漏、长事务、慢 SQL、占着连接调外部 API、流量突增、池太小。

## 🧠 完整理解

### 我会先这样理解

数据库连接建立成本高，而且数据库能承受的并发连接有限，所以应用一般维护连接池复用连接。Session/请求需要访问数据库时从池里借连接，用完归还。池大小、overflow、timeout 要和 worker 数、数据库 max connections、请求并发一起算，不能只在单进程里看配置。

### 执行顺序 / 思考顺序

应用启动创建 engine/pool → 请求需要 DB 时 checkout 连接 → 执行事务 → close/Session close 把连接 checkin → 空闲连接复用；池耗尽时新请求等待，超过 pool timeout 则报错。

### 容易踩的坑

池开得越大不一定越快，可能把数据库压垮。连接泄漏、长事务会让池很快耗尽。多进程 worker 通常每个进程都有自己的连接池，总连接数要乘起来。

### 面试时我会这样说

> 我排“数据库突然超时”时不只看 SQL，也会看连接池。比如 4 个 worker，每个 pool_size=20，理论上就可能占 80 条连接。长事务不释放连接时，接口会表现成大家都在等池。

## 最小代码 / 场景

```text
request -> pool wait -> active conn -> SQL -> release
```


## 🧪 简单例子与返回结果

### 例子

```text
pool_size = 5
同时来了 8 个需要数据库连接的请求
```

### 运行 / 返回结果

```text
最多 5 个请求先获得池内连接；
其余请求等待连接被归还（或达到超时后失败）。
```
