# ORM N+1

## 一句话理解

先查 N 条主记录，再为每条关联数据额外查一次，形成 1+N 查询。

## 核心理解

通过 SQL 日志/查询计数发现；用 selectinload/joinedload/JOIN/批量查询解决。

## 🧠 完整理解

### 我会先这样理解

N+1 是 ORM 里非常典型的性能问题：先用 1 条 SQL 查出 N 个父对象，随后访问每个对象的关系属性时又各发 1 条查询，最终变成 1+N 次。数据量小时很隐蔽，上线后 N 变大，网络往返和数据库解析成本会迅速放大。解决重点是提前明确需要哪些关联数据并使用合适的 eager loading。

### 执行顺序 / 思考顺序

SELECT users 一次得到 N 个 user → 循环 `user.tasks` → 每次 lazy load 发 `SELECT tasks WHERE user_id=?` → N 个额外查询。改用 selectinload 通常变 2 次查询，joinedload 常变 1 次带 JOIN 查询。

### 容易踩的坑

不要只用“查询次数越少越好”判断。joinedload 对一对多可能产生大量重复行；selectinload 会多一条 IN 查询。要按关系基数和数据量选择。

### 面试时我会这样说

> 我排 ORM 慢接口会先看 SQL 日志有没有 N+1。典型就是先查 100 个 user，然后循环访问 tasks，结果又打 100 次 SQL。通常我会根据关系大小选 selectinload 或 joinedload，而不是让 lazy load 悄悄发生。

## 最小代码 / 场景

```python
stmt=select(User).options(selectinload(User.tasks))
```


## 🧪 简单例子与返回结果

### 例子

```python
users = (await db.execute(select(User))).scalars().all()
for user in users:
    print(user.tasks)  # 若 tasks 是懒加载，可能每个 user 再查一次
```

### 运行 / 返回结果

```text
如果有 100 个 user：
1 次查询 users
+ 最多 100 次查询各自 tasks
= 典型情况下 101 次查询
```
