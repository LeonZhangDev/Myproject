# 索引选择性

## 一句话理解

条件越能把数据缩小到很小范围，选择性通常越高。

## 核心理解

email 几乎唯一，选择性高；二值状态列常选择性低。

## 🧠 完整理解

### 我会先这样理解

选择性可以粗略理解为“一个条件能把数据缩小到什么程度”。高选择性列例如唯一邮箱，过滤后只剩极少行，索引通常很有价值；低选择性列例如布尔状态，单独索引可能仍要访问大量行，收益有限。数据库优化器会结合统计信息和数据分布决定是否使用索引。

### 执行顺序 / 思考顺序

统计列的不同值数量/分布 → WHERE 条件给出某个值或范围 → 优化器估算匹配行比例 → 计算索引访问与顺序扫描成本 → 选择更便宜的计划。

### 容易踩的坑

“字段重复多就永远不能建索引”也太绝对。低选择性列与高选择性列组合成复合索引，或在特定 partial index 场景里仍可能很有价值。

### 面试时我会这样说

> 我会把选择性理解成“这个条件能筛掉多少数据”。像 gender 单列通常区分度低，email 区分度很高。但最终不是靠经验拍脑袋，我还是会看真实数据分布和执行计划。

## 最小代码 / 场景

```text
1,000,000 rows -> email match 1 row: high selectivity
```


## 🧪 简单例子与返回结果

### 例子

```text
列 A：gender 只有 2 个值 -> 选择性低
列 B：email 几乎每行都不同 -> 选择性高
```

### 运行 / 返回结果

```text
通常 email 更适合普通 B-Tree 索引定位单条记录；
gender 单列索引在很多查询里收益较小。
```
