# E｜Redis与缓存


## W1-Q31｜缓存与数据库数据不一致时，你会怎样处理？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先明确一致性等级，再以 Cache-Aside 为默认方案，最后讲删除失败、TTL 和强一致场景。

### 参考答案（完整真人口述版）
缓存一致性这个问题我不会先回答“用什么方案”，而是先问业务能接受什么一致性等级。因为用户昵称晚几秒刷新和账户余额错一分钱，显然不是一个问题。

大多数读多写少的数据，我会采用 Cache-Aside，把数据库当最终事实来源。更新时先写数据库并成功提交，然后删除缓存；下一次读缓存 miss，再从数据库读取最新值并回填。相比同时“更新数据库 + 更新缓存”，删除缓存的状态空间更简单，并发写的时候也更不容易因为先后顺序把旧值覆盖回去。

但这仍然不是天然强一致。比如数据库提交成功以后，删除 Redis 失败，就会继续读到旧缓存。所以我会根据重要程度加 TTL、删除重试、消息队列/CDC 异步补偿、版本号等手段，把不一致窗口控制在业务可接受范围。热点数据还要考虑并发读在删除后的瞬间回填旧值这类竞态。

对于余额、库存最终扣减这类强一致核心状态，我不会把 Redis 缓存作为唯一正确来源。正确性必须由数据库事务、唯一约束、条件更新或专门一致性机制兜底，缓存只承担读性能优化。

所以完整回答其实是：**先定义一致性要求，再设计缓存策略；数据库是真相，缓存是副本；允许短暂不一致的地方用补偿缩短窗口，不能错的地方把约束放到数据源。**

### 最小代码 / 场景
```text
UPDATE DB -> COMMIT -> DELETE CACHE
```

## W1-Q32｜Cache-Aside 模式的基本读写流程是什么？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
分别说读 miss 回填和写 DB 后删缓存，再解释为什么常用删除而不是直接更新缓存。

### 参考答案（完整真人口述版）
Cache-Aside 我会记成“**应用自己站在数据库和缓存旁边做协调**”，所以读和写要分开看。

读流程是：先查 Redis，命中直接返回；没命中再查数据库。如果数据库有数据，就序列化后写入 Redis，并设置合适 TTL，再返回给用户。如果数据库也没有数据，为了防止同一个不存在的 id 被反复打到数据库，很多场景会短时间缓存一个空值，但 TTL 会更短。

写流程常见做法是先更新数据库，事务成功以后删除缓存。为什么不是直接更新缓存？因为并发写时“两个存储都更新”会引入更多顺序组合，很容易出现旧请求最后把旧值写回缓存。删除以后让下一次读从数据库重新构建，逻辑相对更稳。

这里仍然要处理异常：数据库失败就不能删缓存当作成功；数据库成功但删缓存失败，需要 TTL、重试或消息补偿；热点 Key 删除后大量请求同时 miss，还可能出现缓存击穿，需要互斥重建等机制。

所以 Cache-Aside 不是一句“先查 Redis 再查 DB”就结束了，完整设计还包括**空值、TTL、并发回填和失效补偿**。

### 最小代码 / 场景
```python
cached=await redis.get(key)
if not cached:
    obj=await session.get(Task,id)
    await redis.set(key,obj_json,ex=300)
```

## W1-Q33｜缓存穿透、缓存击穿和缓存雪崩分别是什么？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先把三者按不存在/热点过期/大面积过期区分，再分别给治理方法。

### 参考答案（完整真人口述版）
这三个概念我喜欢用“**为什么大量请求突然落到数据库**”来区分，这样不容易记混。

缓存穿透是“请求的数据根本不存在”。比如有人不断请求随机 user_id，Redis 没有，数据库也没有，所以每次都完整穿过缓存层。治理通常从参数校验、布隆过滤器、短时间缓存空值入手，恶意流量还要配限流。

缓存击穿是“某一个特别热点的 Key 正好失效”。比如首页热点商品缓存刚过期，几千个请求同一秒都发现 miss，然后一起查数据库。常见做法是互斥重建，让一个请求负责回源，其他请求等待或返回旧值；也可以逻辑过期、提前续期。

缓存雪崩是“大量 Key 同时失效，或者 Redis 整体不可用”。比如所有缓存统一设置 30 分钟，恰好同一批时间到期，回源流量瞬间打到数据库。这里会把 TTL 加随机抖动，做 Redis 高可用、多级缓存、限流熔断和降级，避免数据库跟着被打垮。

我会一句话记：**穿透＝一直查不存在的数据；击穿＝一个热点 Key 被打穿；雪崩＝一大片缓存同时失效。** 名字相近，但故障规模和治理手段不完全一样。

### 最小代码 / 场景
```text
穿透: cache miss + DB miss
击穿: hot key expired
雪崩: many keys expired
```

## W1-Q34｜使用 Redis 实现分布式锁时需要注意哪些问题？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先给正确加锁/解锁原子性，再讲过期与续期，最后强调锁只是互斥手段，不代替幂等和数据库约束。

### 参考答案（完整真人口述版）
Redis 分布式锁我会先说明：一个“看起来能锁住”的实现和一个**在异常情况下还不容易锁错**的实现差别很大。

加锁至少要用类似 `SET lock:key token NX PX 30000`，把“Key 不存在才设置”和“设置过期时间”放在一个原子命令里。不能先 `SETNX` 再单独 `EXPIRE`，因为两条命令之间进程一旦挂掉，可能留下永不过期的死锁。value 也不能随便写 1，而应该是当前持锁者唯一 token。

解锁更关键。不能任务结束就直接 `DEL lock:key`，因为我的锁可能已经超时，随后另一个实例已经获得新锁；这时我再 DEL 就把别人的锁删了。正确做法是通过 Lua 原子地“先比较 token，相同才删除”。

如果业务执行时间可能超过 TTL，还要考虑续期、最大执行时间和故障恢复。即使做了续期，也要意识到网络分区、GC pause、实例宕机等复杂问题，所以涉及极高一致性时不能只靠一个 Redis 锁解决所有问题。

而且锁只负责协调“谁先执行”，**数据正确性还是要靠幂等、数据库 UNIQUE、条件 UPDATE 等底层约束兜底**。比如防止同一个订单重复创建，我希望即使锁失效，数据库约束仍然能挡住第二次写入。

### 最小代码 / 场景
```redis
SET lock:1 token-abc NX PX 10000
```

## W1-Q35｜Redis 的 TTL 和内存淘汰策略有什么区别？常见数据结构怎样选择？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先区分主动过期和内存压力淘汰，再按访问模式选择结构。

### 参考答案（完整真人口述版）
TTL 和内存淘汰策略经常一起出现，但它们解决的其实是两个阶段的问题。

TTL 是业务主动给 Key 设置的生命周期，比如验证码 5 分钟、用户缓存 10 分钟。时间到了以后，这个 Key 逻辑上就应该失效。Redis 会通过惰性删除和定期删除等机制清理过期 Key，并不是简单理解成“时间一到那一微秒就马上物理删除”。

内存淘汰策略是在 Redis 达到 `maxmemory` 以后，内存不够用了，系统必须决定“为了给新数据腾位置，删谁”。不同策略可能在所有 key 或带 TTL 的 key 中按 LRU、LFU、随机等方式淘汰，也可以选择不淘汰直接拒绝写入。所以 TTL 是业务过期语义，eviction 是内存压力下的生存策略。

数据结构我也会按访问模式来选：String 适合简单值、计数、幂等标记；Hash 适合对象字段；Set 适合去重、成员关系；Sorted Set 适合排行榜和按 score 排序；List 可以做简单队列；Stream 更适合需要消费组等语义的消息流。

所以 Redis 设计不是只问“用什么结构”，而是一起考虑：**怎么访问、多久失效、数据量多大、内存满了以后允许牺牲谁。**

### 最小代码 / 场景
```redis
INCR counter
HSET user:1 name Leon
SADD tags python
ZADD rank 100 alice
XADD events * type created
```
