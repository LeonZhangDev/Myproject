# B｜asyncio与并发


## W1-Q8｜Coroutine、Task 和 Future 分别是什么？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
按 Coroutine → Task → Future 的抽象层次解释，并说明谁负责调度、谁表示结果。

### 参考答案（完整真人口述版）
这三个概念我会按“**异步工作本身 → 被调度的任务 → 未来结果的抽象**”这个层次来理解。

调用一个 `async def` 函数时，通常不会马上把里面的代码执行完，而是先得到一个 Coroutine，也就是协程对象。它可以理解成“这段异步工作应该怎么执行”的描述。如果只是创建了协程对象却从来没有 `await` 它或者交给事件循环，它实际上不会按预期完成。

`Task` 是把协程包装成一个可以由事件循环独立调度的任务。比如 `asyncio.create_task(work())` 以后，事件循环就可以让它和其他 Task 交错推进。我可以 `await task` 等结果，也可以取消它、查看它是否完成。业务代码里并发执行多个协程时，Task 是最常直接接触的对象。

`Future` 更底层，它表达的是“现在还没有结果，但未来某一刻会有结果或异常”。Task 本身就建立在 Future 这套语义之上，可以把它理解成“会主动驱动一个协程执行的 Future”。底层库、回调式 API 转 asyncio 时比较容易直接看到 Future。

所以一句话记忆的话：**Coroutine 是待执行的异步逻辑，Task 是事件循环里正在被调度的协程，Future 是对未来结果的通用占位抽象。**

### 最小代码 / 场景
```python
task=asyncio.create_task(work())
result=await task
```

## W1-Q9｜事件循环的作用是什么？协程在什么时候让出执行权？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说 Event Loop 负责调度什么，再明确 await 不等于必然切换，最后解释阻塞代码为什么危险。

### 参考答案（完整真人口述版）
事件循环我会把它理解成 asyncio 的**调度中心**。它不断做几件事：看看哪些 Task 现在可以继续运行、哪些定时器到点了、哪些 socket 或 I/O 已经就绪，然后把执行机会交给对应任务。

协程为什么能并发，关键就在于它不会一直霸占线程。执行到一个尚未完成的可等待操作时，比如网络读取、`asyncio.sleep()`、异步数据库调用，`await` 会让当前协程暂停，把控制权交回事件循环。等这个 I/O 真正完成以后，事件循环再把它放回可运行队列，后面继续执行。

这里有个容易说错的细节：**不是看到 `await` 就一定发生任务切换。** 如果 await 的对象已经完成，它可能马上返回继续执行。真正决定是否让出的是“这个可等待对象当前是否还需要等待”。

反过来，普通同步代码不会自动让出执行权。比如在 `async def` 里写 `time.sleep(5)`，或者做几秒钟纯 Python 大循环，事件循环就被这段代码占住了。同一个 worker 里其他已经就绪的请求也只能等。所以异步程序性能好不好，关键不只是写没写 `async/await`，而是**等待链路是不是真的非阻塞**。

### 最小代码 / 场景
```python
await asyncio.sleep(1)  # 让出
time.sleep(1)           # 阻塞
```

## W1-Q10｜在 async def 中调用阻塞函数会发生什么？应该怎样处理？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说明阻塞事件循环的后果，再区分阻塞 I/O 与 CPU 密集任务的处理方式。

### 参考答案（完整真人口述版）
如果在 `async def` 里直接调用一个耗时的同步阻塞函数，我首先想到的不是“当前请求慢一点”，而是**这个 worker 的事件循环线程可能被整个占住**。在这段阻塞结束以前，其他本来可以继续执行的协程也拿不到调度机会，所以并发一上来，接口延迟会一起升高。

处理时我会先判断这个函数为什么阻塞。如果它是 HTTP、数据库、Redis 这类 I/O，而且有成熟异步客户端，我优先把调用链换成真正的异步版本，这是最干净的方案。如果只有同步 SDK，比如某个老第三方库，可以用 `asyncio.to_thread()` 或线程池，把阻塞 I/O 放到工作线程里，至少不要卡住事件循环。

如果问题是 CPU 密集计算，我不会机械地 `to_thread`。纯 Python CPU 任务还会受到 GIL 和 CPU 竞争影响，而且线程里的重计算一样会抢机器算力。更合适的方案可能是进程池、任务队列、独立推理服务，或者把计算放到 NumPy/PyTorch/GPU 这类底层执行环境。

实际排查这类问题时，我会看请求 P95/P99、Event Loop lag、线程池排队和 CPU 使用率。如果并发一高所有异步接口一起抖动，而且 trace 显示某段同步函数耗时很长，这通常就是很明确的信号。

### 最小代码 / 场景
```python
result=await asyncio.to_thread(blocking_io)
```

## W1-Q11｜asyncio.gather 和 TaskGroup 有什么主要区别？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说共同点，再对比结果收集、异常传播和生命周期管理，最后给选型。

### 参考答案（完整真人口述版）
`gather` 和 `TaskGroup` 都能并发跑多个协程，但我觉得它们的区别不能只记成“一个旧、一个新”，核心是**任务之间的生命周期关系和异常处理方式**。

`asyncio.gather()` 很适合简单的结果聚合：我有 A、B、C 三个协程，想一起启动，然后按传入顺序拿到三个结果。这个 API 很直接，而且 `return_exceptions=True` 还能把异常当作结果收集，适合“多个任务相对独立，我想尽量把结果都拿回来”的场景。

`TaskGroup` 从 Python 3.11 开始更强调结构化并发。所有子任务都被限制在 `async with` 这个作用域里，退出作用域之前会统一收尾。如果其中一个任务异常，TaskGroup 会按规则取消其他未完成任务，并最终以异常组的形式向上抛，任务生命周期更容易推理，不容易留下后台还在偷偷跑的孤儿 Task。

所以我的选择通常是：**独立任务做简单结果收集，用 gather 很顺手；如果这些子任务属于一个整体，一个失败时其他任务也应该结束，我更偏向 TaskGroup。** 真正需要注意的是异常语义，不是只看写法哪一个更短。

### 最小代码 / 场景
```python
async with asyncio.TaskGroup() as tg:
    t1=tg.create_task(a())
    t2=tg.create_task(b())
```

## W1-Q12｜异步任务如何设置超时和正确处理取消？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说超时工具，再讲取消是协作式的，最后强调 finally 清理和 CancelledError 传播。

### 参考答案（完整真人口述版）
异步任务我一般会从两个层面处理：**外层要有超时边界，内层要能正确响应取消并清理资源。**

超时通常放在调用边界，比如访问第三方 HTTP、数据库、LLM 时，不会允许它无限等。我可以用 `asyncio.timeout()`，或者一些库自己的 connect/read/write/pool timeout。这样即使下游卡死，请求也有机会及时释放连接和 worker 资源，而不是无限堆积。

当超时触发时，底层往往会通过取消任务来结束等待。asyncio 的取消是协作式的，Task 会在合适的 await 点收到 `CancelledError`，不是像杀进程一样任意中断。因此代码里如果持有锁、临时文件、数据库事务，就要把清理放进 `finally` 或上下文管理器，保证取消路径也能执行。

还有个我比较在意的坑：不要为了“防异常”写一个很宽的捕获逻辑，然后把取消信号吞掉。清理完成以后，一般应该让 `CancelledError` 继续传播，不然上层以为请求已经正常结束，实际内部任务可能处于一个半完成状态。

所以超时不是简单包一层 `wait_for` 就结束了，完整设计要包括：**超时时间怎么定、取消能否传播、资源怎么释放、操作是不是可重试和幂等。**

### 最小代码 / 场景
```python
async with asyncio.timeout(2):
    await work()
```

## W1-Q13｜单线程协程为什么仍可能发生竞态条件？Lock 和 Semaphore 分别解决什么问题？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先解释单线程为什么仍会交错，再区分 Lock 与 Semaphore，最后提醒尽量减少共享状态。

### 参考答案（完整真人口述版）
单线程协程也会发生竞态，这一点我会先纠正一个常见误区：**竞态不要求两个任务真的在同一个 CPU 时刻并行，只要操作被拆开后可以交错执行，就可能出问题。**

比如一个协程先读 `count=10`，然后中间 `await` 了一次；这时事件循环切到另一个协程，它也读到 10 并写成 11；第一个协程回来后还是基于旧值 10 再写成 11。两个请求都执行了加一，结果却只增加了一次。这就是典型的“读—等待—改—写”竞态。

`asyncio.Lock` 解决的是互斥：某个临界区同一时刻只能有一个协程进入，适合保护共享状态的更新。`Semaphore` 不是要求只能一个，而是限制“最多 N 个同时进入”，所以更常见于并发限流，比如最多同时访问 10 个外部 API，防止把连接池或下游服务打爆。

不过工程上我不会一看到竞态就到处加 Lock。应用进程内的 Lock 只保护当前进程，多个 worker、多个机器之间它完全无效。涉及数据库库存、唯一创建这类跨进程一致性，最终还得靠数据库原子更新、唯一约束、事务或真正的分布式协调。**先减少共享状态，再选择正确作用域的同步手段**，通常比盲目加锁可靠。

### 最小代码 / 场景
```python
lock=asyncio.Lock()
async with lock:
    tmp=count
    count=tmp+1
```

## W1-Q14｜CPU 密集任务为什么不适合直接放在事件循环中？有哪些处理方式？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先解释 CPU 计算为什么不让出 Event Loop，再按任务规模给多进程/队列/独立服务方案。

### 参考答案（完整真人口述版）
事件循环的强项是“**我可以同时等很多事情**”，不是“我可以一直做很重的计算”。CPU 密集任务如果在 `async def` 里连续执行几秒，中间没有真正可等待的 `await`，事件循环就没有机会切换到其他任务。结果即使别的 HTTP 响应、数据库结果已经到了，也只能排队等当前计算结束。

处理方式我会看任务有多重、执行频率多高。偶发的小型 CPU 任务可以考虑 `ProcessPoolExecutor`，利用独立进程绕开单进程 Python 字节码并行限制；执行时间长或者数量多的任务，更适合放到 Celery/RQ 这类任务队列，让 Web 层只负责提交任务和查询状态；模型推理或大规模计算通常直接拆成独立服务，方便单独扩容 GPU/CPU 资源。

还要注意一个细节：有些看起来是“CPU 计算”的库，真正工作是在 NumPy、PyTorch、C/CUDA 底层完成的，它们可能释放 GIL，瓶颈也可能在 GPU，所以不能只看 Python 函数名字判断。最好通过 profiling 和监控确认 CPU 时间花在哪里。

我的总体原则是：**Web worker 负责快速接收请求、I/O 编排和返回结果，不让长时间重计算占住事件循环。** 这样请求延迟和计算任务的资源竞争也更容易分别治理。

### 最小代码 / 场景
```python
from concurrent.futures import ProcessPoolExecutor
```
