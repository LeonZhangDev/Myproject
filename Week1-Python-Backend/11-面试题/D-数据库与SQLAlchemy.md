# D｜数据库与SQLAlchemy


## W1-Q24｜为什么 AsyncSession 不应该在多个并发任务之间共享？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说明 AsyncSession 是有状态事务对象，再讲并发共享会混淆连接/事务/ORM 状态，最后给正确作用域。

### 参考答案（完整真人口述版）
`AsyncSession` 不能在多个并发 Task 之间共享，我会从它的本质来解释：**Session 不是一个无状态的数据库客户端，它本身就是一个带事务和 ORM 状态的工作单元。**

一个 Session 里会记录当前事务、待 flush 的对象、identity map、连接使用状态等。如果两个协程同时拿同一个 AsyncSession，一个正在执行查询，另一个又开始 commit/rollback 或 flush，它们操作的是同一套事务上下文，很容易出现并发操作错误，更严重时业务语义也会混乱——A 任务可能把 B 任务还没准备好的修改一起提交，或者一个 rollback 影响另一个。

所以我通常把 Session 的作用域控制在**一个请求/一个业务事务**。FastAPI 里通过 `Depends(get_session)` 每个请求创建独立 Session，请求结束后关闭。如果一个请求内部又要用 `asyncio.gather()` 并发执行几段都需要数据库访问的任务，我也不会把同一个 Session 丢给这些 Task，而会重新设计：要么数据库操作串行化，要么每个并发任务拿独立 Session，并明确事务边界。

Engine 和连接池可以安全地在应用层共享，但 Session 不一样。这个区分我觉得很重要：**共享的是连接管理基础设施，不共享的是带业务事务状态的 Session。**

### 最小代码 / 场景
```python
# avoid
await asyncio.gather(do_a(session),do_b(session))
```

## W1-Q25｜一个 Web 请求中的 SQLAlchemy Session 通常应如何创建、提交、回滚和关闭？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
按创建 → 使用 → commit/rollback → close 的生命周期回答，并解释为什么每请求独立。

### 参考答案（完整真人口述版）
一个 Web 请求里的 SQLAlchemy Session，我一般会按“**请求开始创建，业务过程使用，成功提交，失败回滚，请求结束关闭**”这个生命周期来设计。

FastAPI 里比较常见的是写一个 `get_session()` 依赖，用 `async with SessionLocal() as session:` 创建 Session，然后 `yield` 给路由或 Service。这样无论接口最后正常返回还是抛异常，离开依赖作用域时都能保证 Session 被关闭，连接归还连接池。

事务提交的位置我会根据业务层设计，不会机械规定所有 commit 都必须写在哪儿。简单 CRUD 可以在 service 完成整个业务后 commit；如果一次请求要同时创建订单、扣库存、写流水，这几个动作应该属于同一个事务，全部成功再 commit，只要中间任何一步失败就 rollback。关键是一个“业务原子操作”不要被随意拆成几个互不相关的 commit。

还有一个容易忽略的点：**Session 关闭不等于事务设计正确。** 如果代码拿着事务又去等待一个很慢的外部 HTTP/LLM 请求，就会让数据库连接和锁被占很久。所以我会尽量缩短事务，只把真正需要原子性的数据库操作包进去。

最终我希望做到的是：每个请求有清晰 Session 边界，每个业务操作有清晰事务边界，异常统一 rollback，最后资源一定释放。

### 最小代码 / 场景
```python
async def get_session():
    async with SessionLocal() as s:
        try: yield s
        except: await s.rollback(); raise
```

## W1-Q26｜flush、commit 和 rollback 分别做什么？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
按 flush 不结束事务、commit 持久化、rollback 回滚来区分，并补充 flush 获取主键/提前暴露约束错误。

### 参考答案（完整真人口述版）
`flush`、`commit`、`rollback` 我会放在同一条事务时间线上理解，而不是分开背三个定义。

`flush()` 的意思是把 Session 里当前积累的 INSERT/UPDATE/DELETE **发给数据库执行**，但事务还没有正式结束。所以数据库生成的主键、某些约束检查通常可以在 flush 后拿到或触发，但只要还没 commit，事务仍然可以 rollback。很多时候 SQLAlchemy 也会自动 flush，比如执行某些查询之前。

`commit()` 才是把当前事务最终提交，让这些修改成为持久结果，并结束这一轮事务。比如创建 User 后再创建关联 Task，我可以先 `flush()` 拿到 user.id，继续写 Task，最后两个操作一起 `commit()`，这样仍然是一个原子事务。

`rollback()` 是当前事务失败时撤销尚未提交的修改，同时把 Session 从失败事务状态恢复出来。特别是发生完整性约束错误以后，如果不 rollback，后面继续使用这个 Session 往往会报“事务已经失败”之类的问题。

所以我会简单记成：**flush 是“把 SQL 发出去但先别盖章”，commit 是“正式确认”，rollback 是“这次事务作废并恢复状态”。** 这三个动作决定的是事务状态，不等同于简单的“保存数据”。

### 最小代码 / 场景
```python
await session.flush()
await session.commit()
# 或 await session.rollback()
```

## W1-Q27｜数据库索引为什么能加速查询？索引是否越多越好？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说索引通过数据结构减少扫描，再讲复合索引/执行计划，最后说明写放大和低选择性。

### 参考答案（完整真人口述版）
索引为什么快，我会先从“**减少需要检查的数据量**”说，而不是只背 B+Tree。没有合适索引时，数据库可能要扫描很多行才能找到目标；有索引以后，可以通过一棵有序的数据结构快速定位到满足条件的记录，再回表读取真正的数据。

比如 `WHERE user_id = ?`、按时间范围查询、JOIN 外键、`ORDER BY created_at`，如果索引设计和查询条件匹配，数据库能少做很多扫描。复合索引还要考虑列顺序，比如 `(user_id, created_at)` 更适合先按 user 过滤、再按 created_at 范围或排序的查询，不是把常用字段随便全塞进去就行。

索引当然不是越多越好。每个索引都要占磁盘和缓存，INSERT/UPDATE/DELETE 时还得同步维护，所以写入会变慢。低选择性字段，比如一个几乎只有 true/false 的列，单独索引也未必能带来收益。还有一种常见情况是“建了索引但 SQL 根本没走”，可能是条件写法、类型转换、数据分布或优化器判断导致的。

所以我在项目里会先从慢 SQL 和真实查询模式出发，再设计索引，最后用 `EXPLAIN` / `EXPLAIN ANALYZE` 看扫描行数、访问方式和实际耗时。**索引是针对查询模式做的数据结构设计，不是给每个字段都加一个加速按钮。**

### 最小代码 / 场景
```sql
CREATE INDEX idx_tasks_user_id ON tasks(user_id);
```

## W1-Q28｜什么是 ORM 的 N+1 查询问题？怎样发现和解决？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先用 1+N 查询过程解释，再说日志发现方法，最后对比 selectinload/joinedload。

### 参考答案（完整真人口述版）
N+1 我会用一个非常具体的过程解释：先 1 条 SQL 查出 N 个 User，然后代码里循环 `for user in users: print(user.tasks)`。如果 `tasks` 是懒加载，ORM 可能为每个 user 再发一条查询，于是总共就变成 **1 + N 条 SQL**。

这个问题在开发数据只有 5 条时几乎感觉不到，但线上一页 100 条、循环再嵌套一层关系以后，查询数会迅速膨胀。接口看起来只是一个普通循环，数据库却被打了上百次，所以它特别隐蔽。我一般会开 SQL 日志、看 APM trace，或者在测试里统计查询次数，发现“同一种 SQL 重复执行很多次”时就会高度怀疑 N+1。

解决方式不是固定用一种 eager load。对于一对多，`selectinload` 很常用：先查主表，再用一次 `WHERE ... IN (...)` 批量查关联数据，通常不会让结果集成倍膨胀。`joinedload` 通过 JOIN 一次带回，某些一对一或数据量小的关系很方便，但一对多数据很多时可能产生大量重复行。复杂查询我也会直接写显式 JOIN 或按业务批量查。

所以核心不是“记住 selectinload”，而是**不要让访问一个 Python 属性在循环里偷偷触发 SQL**。能预判需要哪些关联数据，就在查询阶段一次性规划好加载策略。

### 最小代码 / 场景
```python
stmt=select(User).options(selectinload(User.tasks))
```

## W1-Q29｜Offset 分页和游标分页各有什么优缺点？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说 Offset 简单但深分页和数据漂移问题，再说 Cursor 的稳定排序条件与限制。

### 参考答案（完整真人口述版）
Offset 分页和游标分页我会先看产品到底需要“**按页跳转**”还是“**稳定地继续往后读**”。

Offset 很直观，`LIMIT 20 OFFSET 100` 就是跳过前 100 条拿 20 条。后台管理、数据量不大、需要显示“第 1 页、第 20 页”时很好用。但深分页时，数据库通常仍要定位并跳过前面大量记录，offset 越大成本越高。另一个问题是数据在分页过程中发生插入或删除时，前面的行位置改变，用户可能看到重复数据或者漏数据。

游标分页会记住上一次最后一条记录的位置，比如按 `(created_at, id)` 倒序，下次查询条件是“小于上次最后的 created_at/id”。这样数据库可以沿着索引继续往后找，不需要每次从头数 offset，而且面对新增数据通常更稳定。

不过游标也不是万能的。它不方便直接跳到第 100 页，排序字段必须稳定，最好加唯一字段作为 tie-breaker，否则同一 created_at 下可能出现重复或遗漏。

所以我实际会这样选：**后台小表、需要任意跳页，用 Offset；Feed、聊天记录、订单流水、大表 API，用 Cursor/Keyset 更合适。**

### 最小代码 / 场景
```sql
SELECT * FROM tasks WHERE id<:last_id ORDER BY id DESC LIMIT 20;
```

## W1-Q30｜数据库连接池耗尽通常有哪些原因？如何排查？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
按连接为什么迟迟不归还分类，再给观测顺序，最后说明不要先盲目调大 pool。

### 参考答案（完整真人口述版）
连接池耗尽时，我第一步通常不会马上把 `pool_size` 调大，因为“没连接可用”只是现象，真正问题往往是**连接为什么迟迟没有归还**。

常见原因我会分几类看。第一类是连接泄漏或 Session 没有正常关闭；第二类是事务太长，比如拿着数据库连接又去等待外部 HTTP/LLM；第三类是 SQL 本身慢或被锁住，导致连接一直占着；第四类才是正常业务并发确实超过当前连接池容量。除此之外，还要看数据库自己的 `max_connections`，应用池开得太大也可能直接把数据库压垮。

排查时我会先看应用侧 pool checkout 等待时间、active/idle 数量、超时日志，再看数据库当前 session、长事务、锁等待、慢查询。然后用 APM trace 把一次请求拆开：到底是在“等连接”慢，还是“拿到连接以后执行 SQL”慢。如果 QPS 不高但 active connection 一直不下来，很像泄漏或长事务；如果 SQL span 自己就很长，那要先优化 SQL/索引或锁竞争。

最后才根据稳定 QPS、单请求平均持有连接时间、数据库容量去调 pool。**盲目扩大连接池有时只是在应用层不排队了，转而让数据库本身雪崩。**

### 最小代码 / 场景
```text
request -> pool wait -> SQL -> release
```
