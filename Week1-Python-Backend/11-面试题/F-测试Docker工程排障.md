## W1-Q36｜单元测试和集成测试有什么区别？本项目各测什么？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先按是否隔离外部依赖区分单测/集成，再落到 FastAPI 项目具体测试对象。

### 参考答案（完整真人口述版）
单元测试和集成测试我会先按“**我一次到底验证多大的边界**”来区分。

单元测试尽量把外部世界隔离掉，只验证一个函数、Service 或规则。比如 Pydantic 校验、价格计算、权限判断、缓存 key 生成，这些逻辑没必要每次都启动 PostgreSQL 和 Redis。单测应该快、稳定，而且失败以后能比较直接地定位是哪条规则错了。

集成测试则是故意让多个真实组件一起工作。比如 FastAPI 路由接收请求后，Pydantic 校验、SQLAlchemy 写入 PostgreSQL、事务提交、响应模型序列化这一整条链路能不能跑通；或者缓存 miss 后是否真的查询数据库并写回 Redis。这类测试更接近真实环境，也能发现“单个模块都对，但拼在一起不对”的问题。

在这个后端项目里，我会让业务规则和纯函数主要靠单测覆盖；关键 CRUD、事务、认证、缓存一致性、数据库约束这些跨组件行为用集成测试覆盖。再往上还可以有少量端到端测试验证完整用户流程。

我的原则不是追求某一种测试占比，而是：**越靠底层的规则越快地测，越关键的跨系统边界越真实地测。**

### 最小代码 / 场景
```python
def test_priority_validation():
    with pytest.raises(ValidationError):
        TaskCreate(title='A',priority=99)
```

## W1-Q37｜pytest fixture、mock 和 FastAPI dependency_overrides 分别适合解决什么问题？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
分别从资源复用、替换普通对象、替换 FastAPI 依赖三层说明。

### 参考答案（完整真人口述版）
这三个工具我会按“**谁负责准备环境、谁替换普通依赖、谁替换 FastAPI 依赖图**”来区分。

`pytest fixture` 主要负责测试资源的创建、复用和清理。比如测试客户端、临时 Session、测试用户、初始化数据，都可以放 fixture。它还能控制 function/module/session 作用域，所以测试代码里不用每个用例重复写 setup/teardown。

`mock` 适合替换一个普通外部交互。比如 Service 里会调用支付 API、LLM API、邮件服务，我在单元测试里不希望真的联网，就 mock 返回值；同时还可以断言“这个函数是否被调用、参数是否正确”。这里一个很重要的实践是要 patch **被测试代码实际查找这个对象的位置**，不是机械 patch 它最初定义的位置。

`app.dependency_overrides` 是 FastAPI 专门给 Depends 提供的替换机制。路由如果依赖 `get_db`、`get_current_user`，测试时可以换成测试数据库 Session、固定假用户，而不修改生产路由。

所以一句话：**fixture 管测试生命周期，mock 管普通调用边界，dependency_overrides 管 FastAPI 的依赖注入边界。** 三者经常一起用，但职责并不重复。

### 最小代码 / 场景
```python
app.dependency_overrides[get_session]=get_test_session
```

## W1-Q38｜涉及数据库的自动化测试怎样保证用例相互隔离？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说明隔离目标，再给事务回滚/临时库方案，最后处理并行测试与全局状态。

### 参考答案（完整真人口述版）
数据库测试隔离的目标很简单：**任何一个用例结束以后，都不能把脏状态留给下一个用例。** 不然测试会依赖执行顺序，单独跑能过，一起跑就随机失败。

最常见的做法是每个测试都在独立事务中执行，fixture 提供 Session，用例结束后统一 rollback。这样速度很快，也不用每次重新创建所有表。对于很多 CRUD 和查询测试，这个方案已经足够。

但如果被测代码内部真的会 `commit()`，或者我要验证提交后另一个连接能否读到数据、锁和事务隔离级别等行为，简单外层 rollback 可能不够。这时我会用 savepoint 方案，或者给每个测试/worker 独立 schema、临时数据库，甚至直接用 Testcontainers 启一个真实 PostgreSQL。

并行测试时还要特别处理全局资源：测试账号、Redis key、对象存储路径都要避免固定值冲突，数据库 Session 也不能跨测试共享。测试数据最好生成唯一后缀，不依赖“id 一定等于 1”这种脆弱假设。

所以隔离不是只在最后 `rollback()` 一句，而是要保证**数据库、缓存和其他共享状态都不会跨用例泄漏**。

### 最小代码 / 场景
```python
@pytest.fixture
async def db_session():
    async with TestSession() as s:
        yield s
        await s.rollback()
```

## W1-Q39｜Docker 镜像和容器有什么区别？Dockerfile 与 Compose 分别负责什么？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先用模板/实例类比镜像容器，再区分 Dockerfile 构建与 Compose 编排，最后落到多服务项目。

### 参考答案（完整真人口述版）
Docker 这几个概念我会用“**构建模板**”和“**运行实例**”来区分。

镜像是一个相对不可变的文件系统和运行环境模板，里面包含基础系统、Python 依赖、应用代码、默认启动命令等。容器是镜像真正启动以后形成的运行实例。同一个 `task-api:1.0` 镜像可以同时启动多个容器，每个容器有自己的进程和可写层。

`Dockerfile` 负责回答“这个单个服务的镜像怎么构建”。比如 `FROM python:3.12-slim`，然后复制 requirements、安装依赖、复制代码、设置 CMD。构建结果是一个镜像。

Docker Compose 负责回答“这一组服务怎么一起运行”。比如 API 依赖 PostgreSQL 和 Redis，我可以在 compose 里定义三个 service、环境变量、端口、volume、network、healthcheck，然后一条 `docker compose up -d` 把开发环境拉起来。

还有个常见误区是 `depends_on` 不一定等于“数据库已经完全 ready”，真实项目最好配 healthcheck 或应用重试。数据库数据也要放 volume，否则删容器后可写层一起没了。

所以可以记成：**Dockerfile 是做镜像的配方，Image 是模板，Container 是运行实例，Compose 是多容器的本地/测试编排。**

### 最小代码 / 场景
```bash
docker build -t task-api .
docker compose up -d
```

## W1-Q40｜一个 FastAPI 接口突然变慢，你会按什么顺序排查？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
按先定位慢在哪一层，再用指标/trace 下钻，最后回归验证的顺序回答。

### 参考答案（完整真人口述版）
接口突然变慢时，我不会先凭经验猜“肯定是数据库”，而是按**先确认现象，再定位层级，再找到根因，最后回归验证**的顺序来排。

第一步先把问题描述清楚：是所有接口都慢还是单个接口慢？从什么时候开始？只有某个实例还是全部实例？QPS 有没有突然变大？最近有没有发版？同时看 P50/P95/P99、错误率、吞吐、超时比例。因为平均耗时正常但 P99 暴涨，和所有请求都变慢，排查方向完全不同。

第二步用 request-id / APM trace 把一条慢请求拆开。我会看应用代码耗时、数据库连接池等待、具体 SQL span、Redis 命中率和耗时、外部 HTTP/LLM 调用耗时。这样先判断瓶颈到底在应用、数据库、缓存还是下游，而不是一上来改代码。

第三步结合系统指标继续下钻。CPU 高就看 profiling 和是否有 CPU 密集任务；Event Loop lag 高就查 `async def` 里是不是有阻塞调用；数据库慢就看慢 SQL、`EXPLAIN ANALYZE`、锁等待、长事务和连接池；Redis 慢就看网络、big key/hot key、命中率；外部接口慢就看 timeout、重试是否放大流量。

定位根因以后才针对性处理，比如补索引、去掉 N+1、缩短事务、修阻塞 I/O、增加缓存、限制并发、调整超时或扩容。最后一定用接近原问题的流量重新压测，对比修复前后的 P95/P99、错误率和资源占用。

我觉得性能排查最重要的习惯就是：**先用数据证明慢在哪里，再优化；否则很容易把一个瓶颈修掉，又制造出另一个瓶颈。**

### 最小代码 / 场景
```text
request -> timing -> DB/Redis/API spans -> system metrics -> regression test
```
