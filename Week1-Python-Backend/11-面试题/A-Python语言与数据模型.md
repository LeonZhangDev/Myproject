## W1-Q1｜同步函数、线程和 async 协程有什么区别？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先区分调度方式，再说适用场景，最后补 CPU 密集任务怎么处理。

### 参考答案（完整真人口述版）
这个问题我不会直接背“同步、线程、协程”三个定义，我会先看它们到底是**怎么把等待时间利用起来的**。

同步函数最直观：当前线程执行到哪儿就等到哪儿。比如调用数据库花 200ms，这 200ms 里当前执行流基本就在等，后面的代码不会继续。它的好处是逻辑简单、调试容易，但如果一个服务里同时有很多网络、数据库、Redis 这类 I/O 等待，单纯同步处理的吞吐通常会受限制。

线程是操作系统调度的。一个线程阻塞在 I/O 时，操作系统可以切到另一个线程继续跑，所以它很适合接入大量**同步阻塞库**的场景。不过线程不是免费的，线程多了会有栈内存、上下文切换和共享状态同步这些成本，而且在传统 CPython 里还要考虑 GIL，所以 CPU 密集型任务并不会因为多开线程就自然实现 Python 字节码的多核并行。

`async` 协程的思路又不一样。它通常在一个事件循环里协作式调度，代码执行到一个真正需要等待的 `await` 时，主动把执行权交回事件循环，让别的协程先跑。像 FastAPI 同时等待数据库、HTTP API、Redis、LLM 流式响应时，这种模型往往能用较少线程支撑很多并发连接。

所以我实际选型不会说谁“绝对更快”，而是看任务类型：**同步代码适合简单或低并发流程；线程适合已有同步阻塞 I/O；协程适合高并发 I/O；CPU 密集任务则更倾向多进程、原生扩展、GPU 或独立计算服务。** 如果在 `async def` 里直接做很重的 CPU 计算，反而会把事件循环卡住，这也是异步项目里很常见的坑。

### 最小代码 / 场景
```python
import asyncio
async def io_task(n):
    await asyncio.sleep(1)
    return n
async def main():
    print(await asyncio.gather(io_task('A'),io_task('B')))
asyncio.run(main())
```

## W1-Q2｜Python GIL 是什么？它是否意味着 Python 不能并发？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说明 GIL 限制什么，再明确它不限制什么，最后给出 CPU/I/O 的选型。

### 参考答案（完整真人口述版）
GIL 这个问题最容易回答得太绝对。我理解它的核心是：在**传统带 GIL 的 CPython 进程**里，同一时刻通常只有一个线程在执行 Python 字节码。也就是说，如果两个线程都在做纯 Python 的 CPU 计算，它们不能简单地同时把两个 CPU 核心跑满。

但这不等于“Python 不能并发”，也不等于“多线程完全没用”。比如线程在等待网络、磁盘、数据库时，本来就不需要一直占着 CPU；很多 C 扩展在执行底层计算时也可能释放 GIL，这时候其他线程仍然有机会运行。所以 I/O 密集型程序依然可以通过线程实现很好的并发，`asyncio` 更是通过事件循环在单线程里调度大量 I/O 任务。

如果任务真的是 CPU 密集，比如大量 Python 循环、纯 Python 特征处理，我一般不会指望线程提升多核吞吐，而会考虑 `multiprocessing`、`ProcessPoolExecutor`，或者把计算放到底层能释放 GIL 的 NumPy/PyTorch/C++ 实现中。模型推理还要进一步看是不是跑在 GPU 上，因为瓶颈可能根本不在 Python 字节码。

所以我面试时会把结论说得更准确一点：**GIL 主要限制的是一个 CPython 进程里 CPU 密集型 Python 字节码的线程级并行，不代表 Python 没有并发能力。** 具体用线程、协程还是多进程，最后还是由任务是 I/O 密集还是 CPU 密集决定。

### 最小代码 / 场景
```python
# CPU密集多线程不会因为线程数增加就自然获得 Python 字节码多核并行
def cpu_work():
    return sum(i*i for i in range(10_000_000))
```

## W1-Q3｜为什么不建议把可变对象作为函数默认参数？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说默认参数的求值时机，再解释共享状态问题，最后给标准写法。

### 参考答案（完整真人口述版）
这个坑我会从“**默认参数什么时候创建**”来解释。Python 的默认参数不是每次调用函数时重新计算，而是在函数定义时就创建好了，后面的调用会重复使用同一个默认对象。

如果默认值是整数、字符串这类不可变对象，一般没什么问题；但如果是 `[]`、`{}`、`set()` 这种可变对象，第一次调用对它做了修改，第二次调用拿到的还是同一个对象，所以状态会被保留下来。最典型的现象就是：第一次 `add(1)` 得到 `[1]`，第二次本来以为得到 `[2]`，结果却变成 `[1, 2]`。

这个问题在项目里挺隐蔽，因为单测只调用一次时可能完全看不出来，等函数被重复调用或者并发请求复用以后才暴露。更麻烦的是，别人读函数签名时通常会下意识认为这个列表是“每次调用的新列表”，所以代码行为也违反直觉。

我通常会写成 `items=None`，进入函数后再判断 `if items is None: items = []`。这里最好判断 `is None`，而不是简单写 `if not items`，因为调用方明确传入空列表时，那也是一个合法对象。总结起来就是：**问题不在可变对象本身，而在“默认参数只初始化一次 + 可变对象能被原地修改”这两个特性叠在一起。**

### 最小代码 / 场景
```python
def add(x, items=None):
    if items is None: items=[]
    items.append(x)
    return items
```

## W1-Q4｜浅拷贝与深拷贝有什么区别？什么情况下容易踩坑？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说复制层级，再用嵌套对象解释共享引用，最后说明 deepcopy 也不是无脑使用。

### 参考答案（完整真人口述版）
浅拷贝和深拷贝我通常不会只说“一个复制一层，一个复制所有层”，我会从**引用有没有继续共享**来理解。

浅拷贝会创建一个新的最外层容器，所以 `a is b` 通常是 `False`；但是容器里面如果还放着列表、字典、对象这些引用类型，里面的子对象仍然可能和原对象指向同一块内容。比如 `a = [[1]]`，做一次浅拷贝得到 `b`，再执行 `a[0].append(2)`，你会发现 `b[0]` 也变了，因为两边共享的是同一个内部列表。

深拷贝会递归地复制内部对象，所以大多数普通嵌套结构都能真正隔离开。它适合“我就是需要一份完全独立的配置或数据快照”这种场景。但我不会无脑使用 `deepcopy`，因为复杂对象复制成本可能很高，而且数据库连接、文件句柄、线程锁、模型对象这类资源本身就不应该随便复制；对象之间如果有复杂引用关系，也要考虑复制后的语义是不是还对。

实际开发里我会先问：**我到底要隔离哪一层？** 如果只需要改最外层字段，浅拷贝就够了；如果要修改嵌套内容又不能影响原对象，再考虑深拷贝；很多时候显式构造一个新 DTO 或 Pydantic 模型反而比 `deepcopy` 更清晰。

### 最小代码 / 场景
```python
import copy
a=[[1]]; b=copy.copy(a); c=copy.deepcopy(a)
a[0].append(2)
print(b,c)
```

## W1-Q5｜迭代器和生成器是什么关系？生成器有什么优势？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说明迭代器是协议，生成器是实现方式，再讲惰性计算的价值和限制。

### 参考答案（完整真人口述版）
我会把“迭代器”和“生成器”分成**协议**和**一种方便的实现方式**来理解。

迭代器本质上是一个可以不断拿“下一个值”的对象，核心协议就是 `__iter__()` 和 `__next__()`。每次调用 `next()` 得到一个元素，直到没有数据时抛出 `StopIteration`。所以像文件对象、很多数据库游标，本质上都可以表现成迭代器。

生成器是 Python 帮我们简化了迭代器写法。一个函数里只要出现 `yield`，调用它时不会立刻把整个函数执行完，而是返回一个生成器对象。每次消费一个值时，代码从上次 `yield` 暂停的位置继续执行。这样就不需要自己手写一个类去维护 `__next__` 和内部状态。

生成器最大的价值是**惰性计算**。比如我要处理 1000 万行日志，如果先全部读进列表，内存压力会很大；生成器可以一行一行读、一行一行处理。SSE 或流式输出也是类似思想：有数据就往外产出，不需要等全部结果准备好。

它也有边界：生成器一般只能顺序消费，消费完就没了，也不适合随机索引。所以一句话总结就是：**生成器通常是迭代器，但迭代器不一定通过生成器实现；生成器的优势主要是按需计算和降低内存占用。**

### 最小代码 / 场景
```python
def numbers():
    yield 1
    yield 2
for x in numbers(): print(x)
```

## W1-Q6｜Python 装饰器的本质是什么？为什么常使用 functools.wraps？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先把装饰器还原成函数替换，再讲闭包和典型用途，最后解释 wraps 对框架的影响。

### 参考答案（完整真人口述版）
装饰器我一般不会从 `@decorator` 这个语法开始背，我会先把它还原成普通函数调用。比如 `@log` 放在 `pay()` 上面，本质上可以理解成定义完函数以后执行了一次 `pay = log(pay)`。也就是说，装饰器接收原函数，再返回一个新的可调用对象，把原函数“替换”掉。

这样做最大的价值是：**不改原函数内部代码，也能统一加一层横切逻辑。** 比如权限校验、日志、重试、缓存、统计耗时、事务处理，都很适合放在函数调用前后。函数装饰器里通常会定义一个 `wrapper`，而这个 `wrapper` 又引用了外层传进来的原函数，所以这里也经常同时用到闭包。

`functools.wraps` 我基本会默认加。原因是如果不加，装饰以后 `pay.__name__` 可能变成 `wrapper`，`__doc__`、注解等元信息也可能丢失。对于普通脚本这可能只是日志不好看，但对 FastAPI 这类会检查函数签名、注解、文档信息的框架，元数据丢失有时会带来更实际的问题。

另外还有一个容易被追问的点：带参数的装饰器为什么多一层函数？因为这时第一层先接收装饰器参数，第二层才接收真正的原函数，最后再返回 wrapper。只要把它不断还原成“函数接收函数、再返回函数”，语法就没那么神秘了。

### 最小代码 / 场景
```python
from functools import wraps
def deco(fn):
    @wraps(fn)
    def wrapper(*a,**kw): return fn(*a,**kw)
    return wrapper
```

## W1-Q7｜上下文管理器解决什么问题？with 语句如何保证资源释放？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说它管理资源生命周期，再解释 enter/exit 与异常，最后给常见场景。

### 参考答案（完整真人口述版）
上下文管理器我理解成是专门解决“**资源的生命周期必须成对管理**”的问题。像文件、数据库连接、事务、锁这类资源，都不是拿到以后用完就不管了，而是必须保证最后能关闭、释放、提交或回滚。

`with` 的好处是把“进入”和“退出”绑定到一个明确的代码作用域里。同步上下文管理器底层通常对应 `__enter__()` 和 `__exit__()`：进入 `with` 时获取资源，离开代码块时执行清理。最重要的是，即使代码块中间抛异常，退出逻辑仍然会被执行，所以比到处手写 `close()`、`release()` 更不容易漏。

异步场景也是一样，只是接口变成 `__aenter__ / __aexit__`，配合 `async with` 使用。比如 SQLAlchemy 的 AsyncSession、事务上下文、`asyncio.Lock` 都很常见。

所以实际项目里我看到一个资源如果有明确的“申请—使用—释放”过程，我会优先考虑上下文管理器。它本质上不是为了让代码看起来更短，而是为了**把清理动作变成结构化保证**，尤其是异常路径也能正确执行，这才是它最重要的价值。

### 最小代码 / 场景
```python
with open('a.txt','w') as f:
    f.write('ok')
```
