## W1-Q15｜FastAPI 依赖注入解决了什么问题？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说 DI 把公共能力从路由拆出去，再讲生命周期与测试替换，最后举 Session/认证。

### 参考答案（完整真人口述版）
FastAPI 的依赖注入我理解成不只是为了“少写几行代码”，它更重要的是把**公共依赖的获取、复用和生命周期管理从业务函数里拆出去**。

比如一个路由可能需要数据库 Session、当前登录用户、权限判断、分页参数。如果每个路由都自己创建 Session、解析 Token、判断角色，代码很快就会重复，而且这些逻辑和真正的业务逻辑混在一起，很难测试。通过 `Depends`，路由只声明“我需要什么”，FastAPI 负责按依赖图把这些对象准备好。

它还有一个很实用的点是依赖可以继续依赖别的依赖。比如 `get_current_user` 可以依赖 `get_token`，`require_admin` 又依赖 `get_current_user`。这样认证和授权层次会比较清楚。对于带 `yield` 的依赖，FastAPI 还能帮我们管理进入和退出，比如每个请求创建一个 Session，请求结束后统一关闭。

测试时也很好用，因为可以通过 `app.dependency_overrides` 把真实数据库、真实用户替换成测试对象。所以我会把它总结成：**依赖注入解决的是公共资源、公共校验和业务代码之间的解耦，同时让生命周期和测试替换更可控。** 但像真正的业务流程，我不会为了“依赖注入”硬拆成一堆 Depends，那样反而会让依赖图难读。

### 最小代码 / 场景
```python
@app.get('/tasks')
async def tasks(session=Depends(get_session)):
    ...
```

## W1-Q16｜Pydantic 校验和数据库约束有什么区别？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先分应用层与持久化层，再解释两层都做的原因，最后用 unique/not null 举例。

### 参考答案（完整真人口述版）
Pydantic 校验和数据库约束我会把它们看成**两道不同位置的防线**，不能互相替代。

Pydantic 在应用入口比较靠前，主要负责“这个请求在业务层看起来是否合法”。比如字段是不是整数、字符串长度是否合理、日期格式是否正确、某两个字段之间有没有逻辑关系。它的优势是能尽早给客户端一个清晰的 422 错误，不需要真的打到数据库。

数据库约束解决的是更底层的数据完整性，而且它必须面对并发。比如 `email UNIQUE`，两个请求几乎同时都先在应用层查询“这个邮箱不存在”，然后一起创建。如果只靠 Pydantic 或业务里的 `if` 检查，两边都可能通过；最终只有数据库的 UNIQUE 约束能从数据层保证不会插入两个相同邮箱。`NOT NULL`、外键、CHECK 也是类似。

所以我的原则是：**能在 Pydantic 提前发现的问题提前发现，能由数据库保证的不变量一定让数据库兜底。** 两层都做不是重复，而是职责不同：前者提升接口体验和业务可读性，后者保证无论请求来自哪里、并发多高，最终数据都不会破坏核心约束。

### 最小代码 / 场景
```sql
ALTER TABLE users ADD CONSTRAINT uq_email UNIQUE(email);
```

## W1-Q17｜ASGI 和 WSGI 有什么区别？为什么 FastAPI 通常运行在 ASGI 服务器上？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说明协议接口模型差异，再说异步、WebSocket、长连接，最后落到 FastAPI/Uvicorn。

### 参考答案（完整真人口述版）
WSGI 和 ASGI 我不会只记“一个同步、一个异步”，我会从它们支持的**连接模型和应用协议**来区分。

WSGI 是传统 Python Web 的标准接口，模型更偏向一次请求进来，应用同步地产生一次响应。Flask、早期 Django 这类生态最典型。对于普通同步 HTTP 请求它很成熟，但原生处理长连接、WebSocket、大量异步 I/O 就不够自然。

ASGI 是后来的异步服务器接口，它本身就是围绕异步调用设计的，不只支持普通 HTTP，还能更自然地承载 WebSocket、长连接和事件驱动场景。FastAPI/Starlette 的请求处理、异步依赖、SSE、WebSocket 都和这个模型很契合，所以通常会跑在 Uvicorn、Hypercorn 这类 ASGI Server 上。

不过 ASGI 并不意味着“只允许 async”。FastAPI 里普通 `def` 路由也能工作，框架会针对同步函数做线程池等适配。真正的价值是：**整个服务器和框架具备异步并发能力，可以在同一个应用里同时处理同步和异步工作负载。**

### 最小代码 / 场景
```bash
uvicorn app.main:app --reload
```

## W1-Q18｜FastAPI 路由应该使用 def 还是 async def？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
不要用固定规则死选，先看内部调用是异步还是阻塞，再说明 FastAPI 对 def 的处理与 async def 的风险。

### 参考答案（完整真人口述版）
FastAPI 路由用 `def` 还是 `async def`，我不会按“async 看起来高级”来选，而是看**这条调用链会不会阻塞事件循环**。

如果路由内部调用的数据库、HTTP、Redis SDK 都是异步的，比如 `await session.execute()`、`await httpx_client.get()`，那我会用 `async def`，让等待 I/O 时把执行权交出去，这正是异步框架的优势。

如果业务依赖的是一个同步阻塞库，而且短期内没法换成异步版本，直接把它塞进 `async def` 反而危险，因为同步调用会把事件循环卡住。这种情况下可以让路由本身用普通 `def`，FastAPI/Starlette 通常会在线程池里执行它；或者在异步路由中明确用 `asyncio.to_thread()` / 线程池隔离这段阻塞操作。

还有一种是 CPU 密集任务。无论写 `def` 还是 `async def`，长时间 CPU 计算都不是 Web worker 最理想的地方，通常应该进一步拆到进程池、任务队列或独立计算服务。

所以我的判断标准很简单：**异步 I/O 链路用 async def；同步阻塞链路不要假装异步；CPU 重任务尽量移出 Web 请求路径。**

### 最小代码 / 场景
```python
@app.get('/bad')
async def bad():
    time.sleep(5)
```

## W1-Q19｜中间件与依赖注入分别适合处理什么逻辑？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先按作用范围区分：全局请求链用中间件，路由级可组合逻辑用依赖；再讲测试和异常边界。

### 参考答案（完整真人口述版）
中间件和依赖注入都能在路由前后执行逻辑，所以看起来有点像，但我会按它们作用的**范围和语义**来区分。

中间件包在整个 HTTP 请求链路外面，通常所有请求都会经过。像 request-id、统一访问日志、耗时统计、CORS、全局 header 处理，这些逻辑跟具体某个业务路由没有关系，就很适合中间件。它能看到完整 Request 和 Response，也适合做全局观测。

依赖注入更贴近路由本身，可以按路由、Router 或具体参数选择性使用，而且依赖结果还能直接作为业务函数参数传进去。所以数据库 Session、当前用户、RBAC 权限、分页参数、某类业务前置校验，我更倾向用 Depends。

比如“每个请求都生成 request_id”我会放中间件；“只有管理员接口才检查 admin 权限”就放依赖。认证有时两边都能做，但我更喜欢让路由显式声明自己需要什么权限，代码可读性更强。

总结就是：**中间件适合全局、协议层、横切逻辑；依赖适合可组合、可注入、和具体接口语义有关的资源与校验。**

### 最小代码 / 场景
```python
@app.middleware('http')
async def mw(request,call_next):
    return await call_next(request)
```

## W1-Q20｜FastAPI lifespan 适合管理哪些资源？为什么不应在每个请求中重复初始化？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先列应用级昂贵资源，再说明一次初始化和统一关闭的价值，最后区分每请求资源。

### 参考答案（完整真人口述版）
`lifespan` 我把它理解成 FastAPI 应用级别的**启动和关闭生命周期管理**。有些资源创建一次以后可以被所有请求复用，就没必要每个请求都重新初始化。

最典型的是数据库 Engine/连接池、Redis Client、HTTP Client、模型、向量索引、配置缓存这类长生命周期资源。应用启动时创建，服务运行期间复用，关闭时统一释放。尤其是 HTTP Client，如果每个请求都重新建连接，会失去连接池和 keep-alive 的价值；大模型或 embedding 模型如果每次请求都加载，更是完全不可接受。

但这里要区分“应用级对象”和“请求级对象”。比如 SQLAlchemy Engine 适合全局复用，而 Session 通常不适合做成一个全局单例，因为 Session 带着事务和 ORM 状态，应该按请求创建、请求结束关闭。Redis client 通常能全局复用，但具体 pipeline/transaction 也可能有更小的作用域。

所以我使用 lifespan 时会问两个问题：**这个资源初始化成本高不高？它能不能安全地跨请求共享？** 能共享的放应用生命周期，带请求状态的继续放 request scope，这样性能和隔离性都比较合理。

### 最小代码 / 场景
```python
@asynccontextmanager
async def lifespan(app):
    app.state.client=AsyncClient(); yield; await app.state.client.aclose()
```

## W1-Q21｜BackgroundTasks 适合做什么？为什么不能把它当作可靠任务队列？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先说适合的轻任务，再解释同进程、无持久化/重试的限制，最后给可靠任务队列替代。

### 参考答案（完整真人口述版）
`BackgroundTasks` 我会把它定位成“**响应已经可以先返回，但还有一点轻量后续工作要做**”，而不是一个真正的分布式任务系统。

比如用户创建记录成功以后发一封不太关键的通知邮件、写一条辅助日志、做一个很短的文件后处理，这类任务即使晚一点执行也没关系，而且执行时间比较短，用 BackgroundTasks 很方便。它不需要额外部署 Celery 或队列，代码也简单。

但它和当前 Web 进程绑得很紧。进程如果重启、崩溃、被容器杀掉，任务可能就丢了；它也没有完整的持久化、重试、任务状态、优先级、分布式消费这些保障。更重要的是，如果后台任务本身是很重的 CPU 或长时间阻塞任务，它仍然会占这个服务实例的资源，影响正常请求。

所以像“订单扣款后必须保证最终发货”“几十分钟的数据处理”“模型训练/批处理”这类关键任务，我会用 Celery、RQ、消息队列或专门的任务服务。**BackgroundTasks 适合轻量、非关键、短任务；可靠任务要交给真正的持久化队列。**

### 最小代码 / 场景
```python
background_tasks.add_task(write_log,'created')
```

## W1-Q22｜为什么要区分请求模型、数据库模型和响应模型？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
按 API 输入、持久化、API 输出三种职责解释，再说明安全、演进和解耦。

### 参考答案（完整真人口述版）
请求模型、数据库模型、响应模型我会刻意分开，因为它们其实代表三个完全不同的边界。如果全部复用一个模型，项目刚开始看着省事，后面权限、安全和字段演进会很容易混在一起。

请求模型表达的是“客户端允许传什么”。比如创建 User 时允许传 `email`、`password`，但不应该让客户端自己传 `id`、`is_admin`、`created_at`。数据库 ORM 模型表达的是“系统内部怎么持久化”，里面可能有密码哈希、外键、关系、内部状态，这些字段并不适合直接暴露给 API。

响应模型表达的是“我承诺给客户端什么”。比如数据库里有 `password_hash`，响应里一定不应该带出去；又比如内部有十几个字段，但公开 API 只需要 id、name、created_at。通过独立响应模型，FastAPI 还能帮我们做一次输出过滤和类型约束。

这种分层还有一个工程价值：以后数据库表结构变化，不一定要把 API 契约一起改；API 增加兼容字段，也不必污染 ORM。所以我会把它概括成：**请求模型保护输入边界，ORM 模型负责持久化，响应模型保护输出契约。** 分开以后代码确实多一点，但长期维护会稳很多。

### 最小代码 / 场景
```text
TaskCreate -> Task ORM -> TaskOut
```

## W1-Q23｜SSE 和 WebSocket 分别适合什么场景？

### 先自己回答
> 先按自己的理解口述 60~90 秒，再看下面；不要逐字背答案。

### 回答逻辑
先看通信方向，再比较协议和典型场景，最后说明 LLM 为什么常用 SSE。

### 参考答案（完整真人口述版）
SSE 和 WebSocket 我主要看通信是不是需要**双向、实时、持续**。

SSE 本质上还是 HTTP 长连接，由服务器持续往客户端推文本事件，通信方向主要是 Server → Client。它的好处是协议简单、浏览器原生支持 EventSource、断线重连相对方便，而且对很多代理和网关也比较友好。像 LLM token 流式输出、任务进度、日志推送、通知流，这些客户端主要“听服务器说”的场景，我会优先考虑 SSE。

WebSocket 建立后是全双工连接，客户端和服务端都可以随时主动发消息。实时聊天、多人协作、在线游戏、行情交互这类双方都需要频繁推送的场景更适合它。但它的连接状态管理、心跳、重连、水平扩容、网关配置通常也更复杂。

另外如果只是普通请求偶尔返回一个结果，其实两者都没必要，用普通 HTTP 就够了。我的选择逻辑一般是：**单向持续推送优先 SSE；真正高频双向交互用 WebSocket；一次性请求保持普通 HTTP。** 对 LLM 聊天尤其要区分：用户发一条问题还是普通 POST，模型答案的 token 流可以通过 SSE 返回，不一定非要 WebSocket。

### 最小代码 / 场景
```javascript
const source=new EventSource('/stream')
```
