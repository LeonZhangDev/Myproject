# 请求模型、数据库模型、响应模型

## 一句话理解

三者分别表达客户端能传什么、数据库怎么存、接口能返回什么。

## 核心理解

分离能避免敏感字段泄露和表结构与 API 强耦合。

## 🧠 完整理解

### 我会先这样理解

请求模型、数据库模型、响应模型职责不同：请求模型负责“客户端允许提交什么”，ORM 模型负责“数据库怎样存”，响应模型负责“服务允许暴露什么”。三者完全复用看似少写代码，长期却容易把密码、内部字段暴露出去，也会让数据库变更直接绑死 API。边界清晰后，创建、更新和输出还可以分别有不同字段。

### 执行顺序 / 思考顺序

Request JSON → Request Schema 校验 → service 转换/补系统字段 → ORM model 持久化 → 查询得到 ORM → Response Schema 读取允许字段 → JSON 返回。每一层只承担自己的契约。

### 容易踩的坑

不要为了 DRY 追求“一个模型走天下”。重复少量字段往往比安全边界混在一起更可维护；尤其 password、created_by、internal_status 等字段应明确隔离。

### 面试时我会这样说

> 我一般不会把 Pydantic 和 ORM 做成同一个模型。前端能传什么、数据库存什么、最后能返回什么，本来就是三件事。拆开以后虽然多几个类，但接口安全和后续演进会轻松很多。

## 最小代码 / 场景

```text
TaskCreate -> Task ORM -> TaskOut
```


## 🧪 简单例子与返回结果

### 例子

```python
from pydantic import BaseModel

class UserCreate(BaseModel):
    email: str
    password: str

class UserOut(BaseModel):
    id: int
    email: str

incoming = UserCreate(email="a@test.com", password="123456")
response = UserOut(id=1, email=incoming.email)
print(response.model_dump())
```

### 运行 / 返回结果

```text
{'id': 1, 'email': 'a@test.com'}
```

**怎么理解：** 请求模型可以包含 password，但响应模型故意不暴露 password。
