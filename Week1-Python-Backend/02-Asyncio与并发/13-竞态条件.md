# 竞态条件

## 一句话理解

单线程协程也会因为 await 交错执行而破坏共享状态。

## 核心理解

如果“读→改→写”之间存在 await，其他协程可能插进来。

## 🧠 完整理解

### 我会先这样理解

竞态条件指结果依赖多个并发执行单元的时序，而这个时序又不可控。即使 asyncio 通常是单线程，也可能在 await 点切换任务，因此“读取旧值 → await → 写回”仍然会产生丢失更新。数据库并发、线程共享变量、Redis 锁都属于同一类问题：关键是识别需要原子性的临界区。

### 执行顺序 / 思考顺序

任务 A 读 count=0 → A 在 await 处让出 → B 也读到 0 并写 1 → A 恢复后也写 1 → 本来两次加一最后只有 1。解决要么让临界区不被交错，要么使用底层原子操作/事务。

### 容易踩的坑

“单线程就没有竞态”是常见误区。只要执行可以在关键步骤之间被切换，或者状态存放在数据库/Redis 等共享系统里，就仍然有并发竞争。

### 面试时我会这样说

> 我判断有没有竞态会看一件事：这个业务操作是不是由多个步骤组成，而且中间可能让别人插进来。比如先查库存再减库存就是典型的 read-modify-write，必须用行锁、条件更新或其他原子机制保护。

## 最小代码 / 场景

```python
tmp=count
await asyncio.sleep(0)
count=tmp+1
```


## 🧪 简单例子与返回结果

### 例子

```python
import asyncio

counter = 0
async def add_one():
    global counter
    old = counter
    await asyncio.sleep(0)
    counter = old + 1

async def main():
    await asyncio.gather(*(add_one() for _ in range(100)))
    print(counter)

asyncio.run(main())
```

### 运行 / 返回结果

```text
1
```

**怎么理解：** 100 个协程都可能先读到同一个旧值，再覆盖彼此结果，这就是竞态条件。
